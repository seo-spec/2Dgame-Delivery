# 골목길 퀵배송 PRD

## 1. 문서 개요

| 항목 | 내용 |
| --- | --- |
| 제품명 | 골목길 퀵배송 |
| 문서 버전 | 3.0 |
| 구현 기술 | Python + pico2d, 사용자 지정 필수 조건 |
| 작성일 | 2026-11-08 |
| 최종 수정일 | 2026-11-18 — 레이어·부분 스프라이트 기반 타이틀 연출 및 개발 단계 추가 |
| 개발 목표 | 4주 안에 공통 게임 시스템과 3개 스테이지를 구현하고 시연 가능한 상태로 완성 |
| 문서 목적 | 상세 기획을 구현 범위, 기능 요구사항, 데이터, 완료 기준으로 정리 |

이 문서는 상세 기획서를 기준으로 작성한다. 원문의 **확정** 사항은 요구사항으로 유지하고, **제안** 사항은 플레이 테스트로 조정할 초기안으로 구분한다. 원문에 없는 세부 동작은 **미정** 또는 **구현 권장**으로 표시한다. 이전 발표용 기획서는 기준 자료에 포함하지 않는다.

버전 1.1은 사용자 제공 PRD 검토 의견을 반영한다. **권장 수정안**은 원문 확정 사항과 구분한 구현 기준이며, **초기 구현안**의 계산 방식과 동작을 기준으로 개발하되 계수는 플레이 테스트로 조정한다. 아래 QA는 이 수정안을 기준으로 검증한다.

버전 1.2는 사용자 지시에 따라 구현 기술을 **Python + pico2d**로 확정한다. 이는 상세 기획서 이후 추가된 필수 구현 조건이다.

버전 1.3은 pico2d 게임 루프·입력·렌더링·카메라 구조, 이동 장애물의 상대 속도 기반 충돌 피해, 충돌 프레임의 흔들림 회복 제한을 반영한다. 라이브러리 버전은 수업 환경과 일치하는지 확인한 뒤 고정한다.

**[v1.4 추가 — 운석 이벤트]** 사용자 제안에 따라 1단계부터 도로에 주기적으로 운석이 떨어지고 일시적인 통행 불가 구역이 생기는 이벤트를 추가한다. 이 버전의 **[사용자 확정]**은 전달받은 요구사항이며, **[보완 초기안]**은 빠진 동작을 채운 조절 가능한 제안이다. 아래 관련 행은 **[v1.4 추가]**로 표시하고, 상세 규칙과 보완 내역은 5.8에 모은다. 이번 변경은 기획 문서에만 반영하며 구현 완료를 의미하지 않는다. 사용자 표현의 ‘크레이프 자국’은 문서에서 **크레이터(운석 충돌 자국)**로 통일한다.

**[v1.5 보완 — 사용자 검토 반영]** 밀어내기 안전 조건·0.2초 재충돌 유예, 미니맵 차단 잔여 시간, 실제 착지 시각 예고, 9~11초 랜덤 발생 간격, 근처 도로 2~3곳 우선 배정, NPC 생성 제외 및 대기 안전거리를 반영한다. 기존 10초 고정 주기와 전체 맵 균등 선정 규칙은 아래 새 규칙으로 대체한다. 선택지가 있던 표현 방식과 유예의 적용 범위는 **[v1.5 보완 초기안]**으로 구체화한다. 문서 변경만 수행하며 구현은 포함하지 않는다.

**[v1.6 보완 — 추가 검토 반영]** 밀어내기 경로와 거리 제한, 운석 배치의 탈출 경로 보장, 피해 적용 전 착지 확정·취소 절차, 첫 운석 안내를 추가한다. 네 항목의 도입은 사용자 요청이며 구체적인 거리·탐색·표시 값은 **[v1.6 보완 초기안]**으로 구분한다. 관련 검증 기준도 추가하며 게임 코드는 변경하지 않는다.

**[v1.7 보완 — 개발 기준 구체화]** 공통 도로 영역 판정, 원형 크레이터의 이동 경로 충돌, 탈출 경로의 도로 연결성 및 탐색 한도를 추가한다. v1.6의 반경 4배 이동 조건만으로 탈출을 판단하던 초기안을 아래 연결성 기준으로 대체한다. 구체적인 탐색 수치는 **[v1.7 보완 초기안]**이며 성능과 주행 검증으로 조정한다. 이번 변경은 기획 문서에 한정한다.

**[v1.8 변경 — 낙하 가능 영역 확대]** 사용자 플레이 확인에 따라 운석·크레이터는 도로에만 제한하지 않고 보도·빈 땅 등 맵 내부에도 배치할 수 있다. 기존의 ‘도로 내부 전용’ 배치 조건은 이 규칙으로 대체한다. 집·건물은 파괴하거나 손상시키지 않으며 전체 표시 영역과 고정 장애물 충돌 영역을 보호한다. 수령·복귀·모든 배송 구역은 오토바이 충돌 반경의 1.1배만큼 접근 여유를 추가해 크레이터를 제외한다. 접근 여유는 국소 진입 공간 보호이며 전체 경로 연결의 보장은 아니다. 랜덤 묶음의 포위 방지와 도로 탈출 경로 검사는 유지한다. 현재 반영 범위는 수동 크레이터 배치와 공통 배치 제한이며 자동 낙하 기능은 후속 단계에서 연결한다.

**[v1.9 변경 — 크기 무작위 및 3단계 개발]** 사용자 요청에 따라 고정 반경을 최소·최대가 제한된 랜덤 반경으로 변경한다. 초기값은 **반경 34~54픽셀(지름 68~108픽셀)**이며 개체 생성 시 정수 균등 추첨한다. 운석마다 예고 전에 반경과 낙하 시간을 한 번 정하고, 위험 외곽·운석 본체·향후 착지 크레이터와 충돌체가 같은 반경을 사용한다. 예고·낙하 중 반경을 다시 추첨하지 않는다. 크기가 크다는 이유로 경고 시간·피해·차단 시간을 추가 변경하지 않는다. 수치는 조절 가능한 초기값으로 공통 설정 `game/config/meteor.py`에서 관리한다. 수동 크레이터와 단일 운석 예고·낙하에 먼저 적용하며, 착지 크레이터 연결은 4단계에서 구현한다.

**[v2.0 개발 반영 — 4단계 착지·차단]** 단일 운석에 착지 확정·취소, 정지와 화물 착지 피해, 짧은 안전 밀어내기, 0.2초 크레이터 접촉 피해·감속 유예, 같은 크기 크레이터 전환, 개별 착지 3초 뒤 자동 해제를 연결한다. v1.9의 ‘착지 때 연출만 종료’는 이전 단계의 이력이며 현재는 아래 4단계 범위를 따른다. 테스트와 플레이 확인은 사용자가 수행하고 확인 후 커밋한다.

**[v2.1 개발 반영 — 5단계 운석 묶음]** 화물 수령 후 9~11초 간격의 자동 9~10개 묶음 발생, 여러 운석 목록·생성 ID·묶음 번호, 예정 시각 순 착지와 다른 운석 위험 영역을 피하는 보정을 연결한다. 건물·배송 접근·영역 겹침 제한과 개별 랜덤 반경·착지 후 3초 해제는 유지한다. 근처 전방 우선·포위 방지 경로 검사는 6단계, 미니맵은 7단계로 남겨 이번 범위에서 제외한다. 아래 최종 기획 요구사항과 현재 구현 범위를 구분하며 테스트와 플레이 확인은 사용자가 수행한다.

**[v2.2 변경·개발 반영 — 6단계 안전한 랜덤 배치]** 사용자 요청으로 묶음 수량을 **15~18개**로 늘리고 공통 설정에서 조절한다. 화면 안 전방 도로 2~3곳 우선 배정, 부족 시 화면의 다른 도로·전체 맵 보충, 원판 크기와 여유를 반영한 도로 통로 연결 검사, 한도 내 후보 교체·수량 축소·묶음 생략을 구현 범위에 포함한다. 9~11초 간격·반경 34~54·경고 2초·낙하 0.6~1.4초·차단 3초는 유지한다. 이전 버전·단계 이력의 9~10개 및 ‘6단계 미구현’ 설명은 현재 기준으로 대체하며, 미니맵은 7단계로 남긴다. 테스트 실행·플레이 확인·자동 커밋은 수행하지 않는다.

**[v2.3 개발 반영 — 7단계 미니맵과 안내]** 운석·크레이터의 실제 목록과 시뮬레이션 시계에 기반한 미니맵 예고/차단 표시, 차단 잔여 시간에 따른 채움 축소, 수동 영구 차단 구분, 월드 문구 겹침 회피, 수령 전 안내, 첫 실제 자동 묶음의 2초 강조·전용 경고음을 연결한다. 생성이 생략된 0개 묶음은 경보를 발생시키거나 첫 경보 상태를 소비하지 않는다. 수량·배치·충돌·피해 규칙은 변경하지 않는다. 테스트 실행·플레이 확인·커밋은 사용자가 확인한 뒤 수행한다.

**[v2.4 개발 반영 — 8단계 게임 진행 연결]** 기존 운석 사건 처리와 신규 묶음 생성을 분리해 신규 생성은 배송·성공/실패·복귀 판정 후에만 수행한다. 운석 관리자 내부에도 진행 상태·일시정지·종료 가드를 두고, 재시작/종료의 객체·예약·접촉·주기·안내·음원 정리를 명시한다. 긴 멈춤 뒤 경고와 이동을 한 번에 건너뛰지 않도록 모든 게임 시계에 같은 프레임 적용 시간 상한과 하위 시간 단계를 적용한다. 구체 시간 처리 정책은 아래 8단계 구현 보완 기준이며, 운석·배송의 기존 수량·배치·크기·피해·제한시간 수치는 유지한다. 테스트 실행·플레이 확인·커밋은 이번 작업에 포함하지 않는다.

**[v2.5 변경 — 운석주의보 UI]** 사용자 선택에 따라 플레이 중 큰 왼쪽 위 경고 배너를 제거하고 **미니맵 바로 아래의 작은 경고 아이콘·한 줄 상태**로 대체한다. 예고·낙하 중인 실제 운석이 있을 때만 표시하며 마지막 운석 착지/취소 시 접는다. 첫 실제 자동 묶음의 2초 강조와 전용 경고음은 유지하되 이후 1.3초 배너 타이머는 제거한다. 수령 전 학습 안내는 기존 위치에 유지한다. 아래 이전 단계의 큰 배너·고정 1.3초 안내 설명은 이번 기준으로 대체한다.

**[v2.6 변경 — 플레이어 안내 최소화]** 사용자 화면 피드백에 따라 수령 전 ‘운석 주의보 안내’ 상세 패널과 미니맵의 점멸/채움/수동 차단 범례를 모두 제거한다. 플레이어에게는 실제 예고·낙하 중 미니맵 아래 **140×36픽셀의 작은 경고 아이콘 + ‘운석 주의’**만 보여준다. 별도의 설명·수치·상태 단계 문구를 추가하지 않는다. 마지막 운석 착지/취소 후 경고는 접히며, 기존 위험 표시·크레이터·첫 경고음은 유지한다. 이전 버전의 수령 전 설명 유지 요구는 이 기준으로 대체한다.

**[v2.7 변경 — 배송·적재 위치 마커]** 단순한 사각 테두리로만 보이던 월드 구역의 외형을 네 모서리 바닥 마커와 중앙 아이콘으로 바꾼다. 적재는 노란 상자, 배송은 파란 내려놓기 화살표/받침, 복귀는 초록 집 모양으로 구분한다. 현재 배송 대상·적재 구역 진입은 밝게 표시하고 완료 배송지는 차분한 색과 체크 표시로 바꾼다. 실제 사각 판정 범위와 집 이름, Space 안내, 배송·수령·복귀 동작은 그대로 유지한다. 이번 수정은 위치 마커의 시각 표현만 변경한다.

**[v2.8 변경 — 생성 이미지 위치 마커]** 사용자 요청으로 코드 선분 마커를 실제 투명 PNG 자산 4종으로 교체한다. 적재·배송·복귀·완료 이미지는 `assets/images/markers`에 저장하고 생성 프롬프트·자산 정보는 같은 폴더 README에 기록한다. 기존 맵과 어울리는 칠이 벗겨진 페인트/금속 질감을 사용하며 추가 설명 글자는 넣지 않는다. 이미지는 시작 시 한 번 로드하여 공유하고 바깥 투명 여백을 제외한 영역을 실제 구역 크기에 맞춰 표시한다. 건물/바닥 다음, 오토바이 이전에 그려 바닥 마커가 오토바이를 덮지 않게 한다. 판정 구역·Space 안내·적재·배송·복귀 규칙은 유지한다. 이미지 시각·알파 확인과 게임 플레이 확인을 구분하며 실제 게임 실행은 사용자가 수행한다.

**[v2.9 변경 — 운석 수량 증가]** 회당 요청 수량을 15~18개에서 20~24개로 늘린다. 안전 배치 검사에 따라 실제 생성 수량은 줄거나 묶음이 생략될 수 있다. 공통 설정의 최소·최대 수량과 아래 현재 요구사항·검증 기준에 반영한다.

**[추가 — 신호 위반 벌금]** 배송 가능한 시간 동안 실제 이동 방향에 대응하는 교차로 중앙 차도 입구를 차체 앞 가장자리가 넘어갈 때 적색이면 건당 100원을 순수익에서 차감한다. 이전 위치부터 충돌 보정 후 위치까지 원형 차체가 교차로 중앙 사각 영역에 처음 접촉하는 시각과 법선을 연속 검사한다. 도로 가장자리·둥근 모서리 진입도 포함하고 접촉 법선에 대응하는 진입 방향의 실제 신호색을 사용한다. 도로 중앙선과 양쪽 반차선을 포함해 도로 폭 전체에서 실제 진입 방향의 신호를 적용한다. 차선 위치를 바꿔도 적색 신호 판정이 누락되지 않게 한다. 운석 밀어내기는 주행 경로에서 제외한다. 초록불 진입도 기록하며 한 번의 교차로 진입에 최대 한 번만 부과한다. 교차로 안 신호 전환·정지선 주변의 짧은 후진에는 재부과하지 않고, 원형 차체 전체가 교차로 중앙 차도에서 8픽셀 여유까지 벗어나면 새 진입을 허용한다. 이미 교차로 안에서 시작하거나 보정된 경우에는 기존 진입으로 기록해 신호 전환 때 추가 부과하지 않는다. 흰 정지선은 정차 위치를 안내하며 벌금 판정에는 교차로 중앙 차도 경계(도로 폭의 절반)를 사용한다. 흰 정지선을 초록불에 통과했어도 실제 교차로 입구 진입 시 빨간불이면 부과한다. 수령 전·복귀·결과에서는 벌금이 없고 일시정지 시 판정·안내 시간이 멈춘다. 벌금 안내는 화면 위쪽 중앙에 ‘신호 위반! 벌금 100원’을 3초간 표시하고 재시작 시 기록을 초기화한다. 수익 0원에서도 100원을 차감해 음수 순수익을 허용하며, 벌금 → 같은 프레임 배송 정산 → 기존 성공 우선·조기 실패 판정 순으로 처리한다. 기존 수익 목표와 제한시간에 대해 실제 플레이 밸런스 확인이 필요하다.

**[수정 — 위치 마커 비율]** 적재·배송·복귀·완료 PNG는 투명 여백을 제외한 원본 종횡비를 유지해 실제 구역 안에 맞추고 중앙에 표시한다. 세로로 긴 구역에서도 아이콘과 모서리를 늘이거나 압축하지 않는다. 이미지가 차지하지 않는 여백도 기존 구역 판정에 포함한다.

**[v3.0 추가 — 살아 있는 일러스트 타이틀]** 사용자 요청에 따라 레이어 배경과 부분 스프라이트 애니메이션을 조합한 자연스러운 타이틀을 기획한다. 프레임 성능을 고려해 움직이는 요소와 출력량을 제한하고, 시간 기반 재생·사전 로딩·성능 비교·정적 배경 대체 기준을 추가한다. 구체 연출과 수치 예산은 **[보완 초기안]**이며 실제 실행 환경에서 조정한다. 상세 요구사항은 7.2, 개발 순서는 10.1을 따른다. 후속 요청으로 1단계 구조 확인·성능 계측·장면 설계를 수행했으며 결과와 남은 환경 확인 항목은 10.1.1에 기록한다. 2~5단계는 미착수다.

## 2. 제품 개요와 핵심 경험

**[변경 — A~E 마감시간 무작위 배정]** 새 게임·재시작 때 기존 마감시간 45·65·90·115·140초를 A~E에 무작위로 섞어 하나씩 배정한다. A가 항상 가장 빠르고 E가 항상 가장 늦던 고정 순서를 해제한다. 플레이 중에는 배정된 시간을 유지하고 화물 수령 시점부터 함께 계산하며 고객 기분·남은 시간·정산에 동일하게 사용한다. 기존 표의 마감시간은 시간 후보 목록으로 사용하고 각 배송지와의 고정 연결을 해제한다. 전체 배송 제한시간은 150초다.

**[추가 — 십자 교차로 자동 신호]** 북·동·남·서 도로 연결 비트가 모두 있는 십자 교차로에만 신호등을 자동 배치한다. 우측통행 기준 각 진입 방향의 건너편 오른쪽 보도에 기둥을 두고 담당 차선 위로 가로바를 뻗는다. 반대편 두 신호를 같은 방향으로 묶고, 가로 초록/세로 빨강으로 시작해 4초마다 가로·세로 신호를 교대한다. 각 방향의 초록·빨강은 각각 4초이며 전체 주기는 8초다. 신호 시간은 게임 시뮬레이션 시간에 따라 진행하고 일시정지·결과에서 멈추며 재시작 시 초기화한다. 기존 고정 신호 좌표 목록을 도로 연결 기반 배치로 대체한다. 정면 이미지 대신 금속 기둥·가로바·작은 3구 본체를 탑뷰 도형으로 표시하고 가로바는 오토바이 위 레이어에 그린다. 각 진입 차선의 횡단보도 앞에 흰색 정지선을 넣는다. 신호등 기둥·가로바는 충돌 대상으로 등록하지 않는다.

**[추가 — Shift 부스터 효과]** 기존 부스트 조건(W+좌/우 Shift, S 미입력, 전진)에 맞춰 차체 뒤에 주황·노랑·밝은 중심 불꽃과 짧은 속도선을 표시한다. 차체 회전과 카메라 이동을 따르고 부스트 강화에 따라 길이가 늘어난다. Shift 또는 W 해제·후진 시 제거하며, 정지 상태에서는 표시하지 않는다. 시뮬레이션 시간으로만 연출을 갱신해 일시정지·결과에서 멈추고 재시작 시 초기화한다. 매 프레임 11개 선분으로 표시하며 이미지 로드·입자 누적 없이 기존 속도·가속·충돌·화물 피해 수치를 유지한다.

**[추가 — 배송 가능 느낌표]** 배송 중 지정 화물을 보유하고 미완료 배송 구역 안에 들어가면 오토바이 위에 작은 노란 느낌표를 표시한다. 실제 Space 배송 대상과 동일한 판정을 사용하고 카메라·차체 이동에 맞춰 따라다닌다. 구역 이탈·배송 완료·복귀·결과 상태에서는 제거하며 F1과 무관하게 표시한다. 기존 바닥 이미지 마커와 Space 안내, 배송 판정은 유지한다. 별도 이미지 로드나 타이머 없이 HUD 도형으로 표시한다.

플레이어가 탑뷰 2D 환경에서 오토바이를 운전하며 지정 화물을 배달하는 게임이다. 빠르게 달리면 시간을 줄일 수 있지만 급회전과 충돌로 화물이 손상되어 배달 수익이 줄어든다. 플레이어는 집별 마감시간, 기본 배달비, 화물 상태를 함께 고려해 방문 순서와 주행 속도를 선택한다.

### 2.1 핵심 판단

- **속도 조절:** 빠른 주행으로 시간을 확보하되 고속 회전으로 발생하는 흔들림을 관리한다.
- **화물 관리:** 화물마다 독립적인 내구도와 민감도를 고려해 남은 수익을 보존한다.
- **경로 선택:** 각 집의 마감과 기본비를 비교해 자유롭게 배송 순서를 결정한다.
- **[v1.4 추가] 돌발 위험 대응:** 월드와 미니맵의 운석 예고를 보고 낙하 전에 통과하거나, 우회하거나, 차단 해제를 기다린다.

### 2.2 플레이 목표

각 스테이지의 제한시간 안에 모든 지정 화물을 배송하고 목표 수익 이상을 확보한다. 두 조건을 달성하면 배송 타이머가 멈추며, 출발지로 돌아와야 최종 클리어한다.

### 2.3 성공 기준

- 세 스테이지에서 출발, 주행, 배송, 복귀, 결과 확인, 재시작이 이어진다.
- 같은 주행이라도 화물별 민감도와 상태에 따라 손상과 수익이 달라진다.
- 속도와 경로 선택이 배송 시간 및 최종 수익에 영향을 준다.
- 각 스테이지에 제한시간과 수익 목표를 함께 만족하는 실제 주행 경로가 존재한다.

게임은 **Python과 pico2d를 사용해 구현한다.** 대상 연령, 배포 플랫폼, 화면 해상도는 아직 미정이다. Python 및 pico2d 버전과 실행·배포 방식은 프로젝트 초기 설정에서 결정한다.

### 3.2 단계별 범위

1. 1~2주 차에 스테이지 1의 배송부터 복귀까지 완성한다.
2. 3주 차에 자동차·신호등·동적 충돌과 스테이지 2·3을 공통 코드에 연결한다.
3. 4주 차에 보행자를 구현하고 전체 진행, 밸런스, UI와 제출물을 검증한다.

무한 모드는 이번 개발 범위에서 제외한다. 고급 길찾기 AI는 사용하지 않고 미리 정한 경로점으로 교통을 구현한다. 계정, 온라인 기능, 결제 및 별도 성장 시스템은 원문에 없는 추가 범위로 취급한다.

## 4. 게임 흐름과 상태

### 4.1 기본 흐름

1. 타이틀 및 조작 안내에서 게임을 시작한다.
2. 스테이지를 빈 적재 목록으로 시작한다. 배달소 진입로의 수령 구역에서 Space를 새로 누르면 집마다 지정된 화물을 한 번에 수령한다. 중복 수령은 허용하지 않는다.
3. 화물 수령 시점을 출발 시점 `t = 0`으로 삼아 전체 제한시간과 모든 집의 마감을 함께 계산한다. 수령 전에는 배송과 시간 진행을 하지 않는다.
4. 플레이어가 배송 순서와 경로를 선택해 주행한다.
5. 미배송 집의 배송 구역에서 Space를 눌러 배송한다.
6. 배송 시점의 고객 기분과 화물 내구도로 배달비를 정산한다.
7. 전량 배송과 목표 수익을 충족하면 복귀 단계로 전환한다.
8. 출발지 복귀 구역에 도착하면 클리어한다.
9. 결과를 확인한 뒤 다음 단계로 진행하거나 재시작한다.

### 4.2 상태별 동작

| 상태 | 동작 | 종료·전환 조건 |
| --- | --- | --- |
| `DELIVERING` | 주행, 화물 손상, 배송, 타이머 및 수익 갱신 | 전량 배송·목표 달성 시 `RETURNING`, 시간 초과 또는 조기 실패 시 `FAILED` |
| `RETURNING` | 시간제한 없이 복귀, 배송 타이머·수익 고정, 실패 판정 없음 | 출발지 복귀 구역 도착 시 `CLEAR` |
| `CLEAR` | 최종 배송 수와 수익, 성공 결과 표시 | 다음 단계 또는 재시작 |
| `FAILED` | 실패 결과 표시 | 재시작 |

`DELIVERING`, `RETURNING`, `CLEAR`는 원문 상태 설계를 따른다. `FAILED`는 실패 처리를 명확히 표현하기 위한 문서상 상태명이다. 타이틀·선택·결과 UI의 실제 상태명은 구현 시 정한다.

### 4.3 성공과 실패 판정

배송 성공 조건은 `배송 완료 수 == 전체 배송지 수`와 `누적 수익 >= 목표 수익`을 제한시간 안에 함께 만족하는 것이다. 권장 수정안에서는 제한시간과 정확히 같은 시점도 포함한다. 복귀는 시간제한 없이 진행하며 배송 타이머가 정지하고 실패 판정을 수행하지 않는다.

조기 실패는 배송 중에만 다음 식으로 검사한다.

```text
화물별 최대 예상 수익 = floor(기본비 × 1.2 × 현재 내구도 / 최대 내구도)
남은 최대 예상 수익 = 미배송 화물별 최대 예상 수익의 합

누적 수익 + 남은 최대 예상 수익 < 목표 수익이면 즉시 실패
```

- 합계가 목표 수익과 같으면 조기 실패시키지 않는다.
- 이미 배송한 화물은 남은 예상 수익 계산에서 제외한다.
- 고객이 이미 불만 상태여도 상한 계산에는 `1.2`를 사용한다. 원문은 조기 실패 오판을 피하는 보수적 상한으로 이를 제시한다.
- 내구도가 감소하거나 배송을 정산한 뒤 최신 상태로 검사한다.
- 원본 노트의 권장 순서에 따라 배송·손상 갱신 후 성공 조건을 먼저 검사한다.
- 전량 배송했지만 수익이 부족하면 남은 예상 수익이 0이므로 즉시 실패한다.
- 경과시간이 제한시간을 초과했는데 배송 성공 조건을 충족하지 못하면 실패한다.

#### 시간 경계 및 판정 우선순위 (권장 수정안)

- 배송 이벤트의 경과시간 `t <= day_limit`이면 배송을 인정하고, `t > day_limit`이면 새로운 배송을 인정하지 않는다.
- [v2.4 보완] 같은 프레임의 처리 순서는 **적용 시간 결정 → 기존 운석 착지·차단 해제 → 이동·충돌 → 화물 상태 → 프레임 말 배송 입력·정산 → 성공 → 조기 실패 → 시간 초과 → 복귀 도착 → 최종 상태 반영 → 신규 운석 묶음 생성 → 안내·음원 반영**이다. 기존 운석·이동·손상·진행 판정은 하위 시간 단계별로 수행하되 배송 입력은 마지막 단계에서 한 번만 소비하고 신규 묶음도 렌더 프레임당 한 번만 검사한다.
- 충돌과 배송이 같은 프레임에 발생하면 충돌 직접 손상과 화물 상태 갱신을 먼저 반영한 내구도로 정산한다.
- 제한시간 안에 성공 조건을 충족하면 즉시 `RETURNING`으로 전환하고 이후 실패 검사를 건너뛴다.
- `RETURNING`에서는 시간 초과나 충돌로 실패하지 않으며, 화물 내구도와 정산 수익도 변경하지 않는다.
- 배송 입력에 연결된 경과시간을 기준으로 판정한다. 프레임이 제한시간을 넘어갔다는 이유로 배송 시각을 임의로 제한시간에 맞춰 인정하지 않는다. 이벤트 시각을 별도로 기록하지 않는 구현은 입력을 처리한 시뮬레이션 시각을 배송 시각으로 사용한다.

## 5. 기능 요구사항

### 5.1 오토바이 조작

| ID | 요구사항 | 완료 기준 |
| --- | --- | --- |
| MOV-01 | W 입력으로 부호 있는 속도를 증가시킨다. 후진 중이면 먼저 감속 후 전진한다. | 음수 속도에서 W를 유지하면 0을 거쳐 양수로 전환 |
| MOV-02 | S 입력으로 속도를 감소시킨다. 전진 중이면 감속하고 0을 지나 후진한다. | 벽 앞에서 차체를 돌리지 않고 뒤로 탈출 |
| MOV-03 | A/D 입력으로 차체의 좌·우 방향을 회전한다. | 전진·후진·정지 상태에서 방향 조정 가능 |
| MOV-04 | 속도를 전진·후진 최고속도 범위로 제한한다. | 설정 범위를 넘는 가속 방지 |
| MOV-05 | 가속·회전·이동에 `dt`를 적용한다. | 프레임율이 달라도 같은 시간의 이동 결과가 일관됨 |
| MOV-06 | 충돌 시 속도를 감소시키고 맵 밖 이동을 막는다. | 고정 장애물과 경계 통과 방지, 충돌 후 후진 탈출 가능 |
| MOV-07 | Shift+W 유지 시 전진 가속도 배율을 시간에 따라 기본 1배에서 최대 1.8배까지 증가시킨다. | 좌·우 Shift 지원, 최대 배율 제한, 해제 시 기본 가속도 복귀 |

이동 의사코드 (권장 수정안):

```text
W만 입력: 후진 중이면 먼저 brake_accel로 제동, 정지 후 forward_accel × boost_multiplier로 전진 가속
S만 입력: 전진 중이면 먼저 brake_accel로 제동, 정지 후 reverse_accel로 후진 가속
W/S 무입력 또는 동시 입력: speed = move_toward(speed, 0, natural_decel × dt)
speed = clamp(speed, -rev_max, fwd_max)
A/D 입력을 합산해 turn_input을 -1, 0, 1로 계산 (동시 입력은 0)
angle += turn_input × turn_rate × dt
position += direction(angle) × speed × dt
```

#### 입력 및 자연 감속 (권장 수정안)

- W는 전진 방향으로 가속하며, 후진 중에는 먼저 감속한 뒤 전진으로 전환한다.
- S는 전진 중 감속하고 속도가 0이 된 이후에는 후진으로 전환한다.
- W/S 입력이 없으면 자연 감속으로 속도를 점차 0에 가깝게 한다.
- W/S 동시 입력은 가속을 상쇄하고 자연 감속만 적용한다. A/D 동시 입력은 회전을 상쇄한다.
- 정지 상태에서도 A/D 회전을 허용한다. 후진 중에도 같은 회전 입력으로 차체 방향을 조정하고 이동 방향은 속도 부호로 계산한다.
- 자연 감속은 전진·후진 모두에서 작동하며, 0을 지나 반대 방향으로 바뀌지 않는다. `move_toward`는 목표값 0을 넘지 않게 접근하는 연산이다.

전·후진 최고속도, 가속·제동·자연 감속 계수, 회전 속도는 초기 주행 테스트로 결정한다.

#### Shift 전진 가속도 강화 (사용자 추가 요구사항)

- 좌·우 Shift 중 하나 이상과 W를 유지하고 S는 누르지 않은 상태에서, 정지 또는 전진 중이면 전진 가속도 배율을 `dt`에 따라 선형 증가시킨다. 최대 배율은 **1.8배**이며 두 Shift를 함께 눌러도 중첩하지 않는다.
- 초기 구현은 1배에서 1.8배까지 1초로 설정한다. 상승 시간은 조절 가능한 상수로 관리하며 플레이 테스트로 조정한다.
- Shift 또는 W를 놓거나 S를 누르면 배율을 즉시 1배로 초기화한다. Shift만 누르면 가속하지 않으며 W/S 동시 입력은 기존대로 자연 감속한다.
- 후진 중에는 강화하지 않으며, W로 먼저 제동한 뒤 정지·전진 상태에서 배율 상승을 시작한다. 제동 감속도와 후진 가속도는 강화하지 않는다.
- 강화 대상은 전진 가속도와 전진 최고속도다. 사용자 수정 요청에 따라 Shift+W 사용 중 전진 최고속도를 기본의 **1.6배**로 높인다. 초기 수치는 기본 210, 강화 336픽셀/초이며 `BOOST_SPEED_MULTIPLIER`로 조절한다. 후진 최고속도, 회전 속도, 자연 감속도는 유지한다.
- Shift 해제 후 기본 최고속도를 초과한 속도는 즉시 잘라내지 않는다. W 유지 시 자연 감속도로 기본 최고속도까지 내려간 뒤 유지하고, W 해제 또는 W/S 동시 입력 시 기존대로 정지까지 자연 감속한다. S만 누르면 기존 제동 후 후진을 적용한다.
- 적용식은 `boost_multiplier = min(1.8, boost_multiplier + 0.8 × dt / boost_ramp_time)`, `전진 가속도 = forward_accel × boost_multiplier`이다. 연료·게이지·쿨다운은 추가하지 않는다.


#### 일시정지 메뉴 및 주행 초기값 추가

- 기본 전진 최고속도는 210픽셀/초, 전진 가속도는 140픽셀/초²로 조정한다. Shift 전진 가속도는 1초 동안 최대 1.8배, 최고속도는 기본의 1.6배인 336픽셀/초로 강화한다. 후진·제동·자연 감속·회전 수치는 유지한다.
- Esc 새 입력은 즉시 종료 대신 일시정지 메뉴를 열고 다시 누르면 재개한다. 메뉴는 위에서부터 Resume·Restart·Exit이며 방향키·Enter 또는 마우스로 선택한다. Exit와 창 닫기는 게임을 종료한다.
- 일시정지 중 진행 상태는 유지하고 주행·충돌·화물 손상·배송·타이머 갱신을 중단한다. Resume은 기존 상태로 돌아가고, 메뉴 중 유지한 조작 키는 해제 후 다시 눌러야 적용한다. Restart는 기존 전체 초기화 및 배송지 재추첨을 재사용한다.
- HUD와 미니맵의 한글은 설치된 한컴 고딕 Bold를 우선 사용하고 없으면 맑은 고딕 Bold/맑은 고딕으로 대체한다. 영문 메뉴는 Bahnschrift를 우선 사용한다. 글꼴은 초기화할 때만 불러온다.

### 5.2 화물 흔들림과 내구도

사용자 추가 요구에 따라 화물 종류는 일반 화물·취급주의·전자제품·유리제품·소형 화물·도서·꽃·음식·과일·의약품·의류·도자기·화분의 13종으로 구분하고 종류별 작은 아이콘을 사용한다. 배달소 수령 시 13종 중 서로 다른 5종을 무작위 선택해 이번 플레이의 A~E 지정 화물에 연결한다. 수령 전에는 종류와 아이콘을 숨기고 수령 후 하단 화물 패널에 표시한다. 같은 플레이에서 중복 수령하거나 종류를 다시 추첨하지 않으며, 재시작 후 재수령하면 새로 선택한다. 종류 이름과 화물 ID는 별도 관리하고, 종류별 흔들림 손상·충돌 직접 피해 배율을 적용하되 민감도와 최대 내구도는 기존 공통 초기값을 유지한다.

| ID | 요구사항 | 완료 기준 |
| --- | --- | --- |
| CAR-01 | 배송지 수와 같은 수의 화물을 출발 시 적재한다. | 각 단계에서 5·7·9개 적재 |
| CAR-02 | 각 화물의 흔들림·내구도·민감도를 독립 관리한다. | 한 화물의 상태 변경이 다른 화물 값을 덮어쓰지 않음 |
| CAR-03 | 속도와 회전 강도, 민감도에 따라 흔들림을 계산한다. | 고속 급회전의 위험이 저속 회전보다 큼 |
| CAR-04 | 흔들림이 화물별 손상 임계치를 초과한 구간에서 시간에 따라 내구도를 감소시킨다. | 임계치 이하에서는 흔들림에 의한 손상이 없음 |
| CAR-05 | 직진·감속 시 흔들림을 점차 낮춘다. | 회전을 완화하면 흔들림 회복 |
| CAR-06 | 배송 완료 화물을 이후 손상 계산에서 제외한다. | 배송 후 충돌해도 정산 내구도와 금액 유지 |
| CAR-07 | 내구도 0% 화물은 물리 연산을 건너뛰고 0원 배송을 허용한다. | 파손 화물도 지정 집에 배송 가능, 수익 0원 |

화물 유형은 위 13종을 초기 구현 목록으로 사용한다. 초기 내구도, 민감도, 흔들림 단위·최대치, 손상 임계치, 증가·회복·손상 계수의 최종 밸런스는 미정이며 현재 코드의 조절 가능한 초기값을 사용한다. 슬라이드의 게이지 수치를 확정 데이터로 사용하지 않는다. 흔들림 회복과 내구도 회복을 구분하며, 원문에는 내구도 복구 기능이 없다.

#### 화물 흔들림 및 내구도 계산 방식 (초기 구현안)

```text
흔들림 증가량 = abs(speed) × abs(turn_input) × 화물 민감도 × 흔들림 계수 × dt
흔들림 회복량 = 흔들림 회복 계수 × dt
현재 흔들림 = clamp(이전 흔들림 + 증가량 - 적용 회복량, 0, 최대 흔들림)
초과 흔들림 = max(0, 현재 흔들림 - 손상 임계치)
내구도 감소량 = 초과 흔들림 × 공통 손상 계수 × dt × 종류별 흔들림 손상 배율
현재 내구도 = max(0, 현재 내구도 - 내구도 감소량)
```

회전 중에는 증가량을 적용하고, 회전 입력이 없으면 증가량을 0으로 한다. 흔들림 회복은 회전 입력이 없거나 플레이어의 감속 조작 및 자연 감속으로 이동 빠르기 `abs(speed)`가 감소한 경우 적용한다. 감속 여부는 충돌 처리 이전의 주행 속도 변화를 기준으로 판단한다. 두 회복 조건을 함께 만족해도 한 번만 적용하며, 충돌이 발생한 프레임에는 회전 입력 유무와 관계없이 적용 회복량을 0으로 한다. 이는 게임 밸런스를 위한 구현 권장안이다.

이전 프레임의 흔들림을 누적 상태로 유지하므로 회전 입력을 놓아도 즉시 0으로 초기화하지 않는다. 감속하면서 회전하는 경우 증가와 회복을 함께 계산하므로 순감소 여부는 계수에 따라 달라진다. 실제 테스트에서 감속에 따른 완화가 체감되도록 조정한다.

전진·후진 모두 `abs(speed)`를 사용하며 화물별 민감도와 임계치로 손상 차이를 만든다. 최대 흔들림과 계수는 플레이 테스트로 조정한다. 흔들림이 낮아져도 이미 감소한 내구도는 회복되지 않는다. 배송 완료 및 내구도 0% 화물은 이 연산에서 제외한다.

#### 화물 종류별 손상 배율 (조절 가능한 초기값)

공통 흔들림 손상 계수는 0.2에서 0.1로, 공통 충돌 직접 피해 계수는 0.05에서 0.025로 낮춘다. 각 기본 피해량에 아래 해당 배율을 한 번만 곱한다. 종류별 설정은 `game/config/cargo_types.py`에서 관리하고 수령 시 Cargo 인스턴스에 복사한다. 종류가 없는 화물은 1.0을 사용한다. 최대 내구도·흔들림 증가·회복·임계치는 유지하고 배송 완료·파손 화물은 제외하며 내구도는 0 아래로 내려가지 않는다. F1에서 배율을 확인할 수 있다.

| 종류 | 흔들림 손상 배율 | 충돌 직접 피해 배율 |
| --- | --- | --- |
| 일반 화물 | 1.0 | 1.0 |
| 취급주의 | 1.4 | 1.4 |
| 전자제품 | 1.2 | 1.3 |
| 유리제품 | 1.6 | 1.6 |
| 소형 화물 | 0.8 | 0.8 |
| 도서 | 0.6 | 0.7 |
| 꽃 | 1.3 | 1.1 |
| 음식 | 1.2 | 1.0 |
| 과일 | 1.1 | 1.2 |
| 의약품 | 1.2 | 1.1 |
| 의류 | 0.4 | 0.5 |
| 도자기 | 1.5 | 1.6 |
| 화분 | 1.1 | 1.4 |

일반 화물은 초과 흔들림 50에서 초당 내구도 5, 충돌 속도 180에서 내구도 4.5가 감소한다. 유리제품은 각각 8과 7.2로, 종류별 차이는 있지만 이전 공통 피해량보다 낮다. 배송 정산·조기 실패 계산은 배율이 반영된 현재 내구도를 그대로 사용한다.

### 5.3 충돌

- 건물, 주차 차량, 전봇대 등 고정 장애물과 충돌을 처리한다.
- 사용자 추가 요구사항에 따라 실제 배치된 고정 오브젝트 전체를 충돌 대상으로 한다. 현재 샘플의 주택·상가·배달소·나무·화단·정류장·벤치·분리수거함·우편함·분수에 개별 충돌 영역을 정의한다. 신호등 기둥·가로바는 사용자 결정에 따라 충돌에서 제외한다. 도로·보도·횡단보도·배달소 진입로는 바닥으로 취급해 통행을 막지 않는다. 차량·전봇대는 현재 샘플에서 제외한 상태를 유지한다.
- 이동 자동차 등 동적 장애물과의 충돌을 처리한다.
- 충돌 시 오토바이 속도를 감소시키고 현재 적재 중인 모든 화물에 직접 손상을 적용한다.
- 충돌 직접 손상은 급회전의 흔들림 손상과 별도 경로로 계산한다.
- 접촉 상태가 유지되는 동안 매 프레임 피해가 반복되지 않도록 장애물별 접촉 시작을 관리한다.
- 배송 완료 화물은 충돌 피해 대상에서 제외한다.

#### 충돌 피해 처리 방식 (초기 구현안)

```text
고정 장애물 충돌:
충돌 속도 = abs(오토바이 충돌 직전 속도)

이동 장애물 충돌:
충돌 속도 = length(오토바이 충돌 직전 속도 벡터 - NPC 충돌 직전 속도 벡터)

충돌 피해량 = 충돌 속도 × 공통 충돌 피해 계수 × 종류별 충돌 직접 피해 배율
현재 내구도 = max(0, 현재 내구도 - 충돌 피해량)
```

감속·위치 보정 전의 속도를 저장해 현재 적재 중인 모든 화물의 직접 피해를 계산한다. 이동 장애물은 자동차 NPC를 대상으로 하며, 두 속도 벡터는 같은 월드 좌표계와 시간 단위를 사용한다. 오토바이 속도 벡터는 `direction(angle) × speed`로 계산해 후진도 반영한다. `length`는 벡터의 크기다. 정지한 오토바이를 움직이는 NPC가 들이받아도 상대 속도에 따른 피해가 발생한다.

배송 완료 화물은 제외한다. 충돌 후 오토바이 속도를 감소시키고 장애물과 겹친 위치를 보정한다.

피해는 해당 장애물과의 접촉이 시작된 순간에만 적용한다. 접촉이 유지되는 동안 추가 피해를 주지 않으며, 접촉 해제 후 새로 충돌하면 다시 적용한다. 별도 시간 기반 재충돌 간격은 초기 구현에 사용하지 않는다.

`RETURNING`에서는 충돌에 따른 이동 제한·감속·위치 보정은 적용하지만 화물 내구도, 수익, 배송 타이머는 변경하지 않는다. 충돌 피해 계수와 속도 감소율은 주행 테스트로 조정한다. 보행자 접촉 페널티는 별도 미정이며 위 공식을 자동 적용하지 않는다.

### 5.4 배송 상호작용

| ID | 요구사항 | 완료 기준 |
| --- | --- | --- |
| DEL-01 | 집과 화물을 1:1로 연결한다. | 다른 화물을 대체 배송할 수 없음 |
| DEL-02 | 방문 순서를 제한하지 않는다. | 미배송 집을 어느 순서로든 배송 가능 |
| DEL-03 | 배송 구역에 진입하면 속도와 관계없이 Space 안내를 표시한다. | 고속 통과만으로 배송되지 않음 |
| DEL-04 | 배송 구역 안에서 Space를 새로 누르면 속도와 관계없이 즉시 배송한다. | 조건 충족 시 해당 집의 화물만 1회 배송 |
| DEL-05 | 배송 시점의 시간·내구도로 보상을 확정한다. | 누적 수익에 건별 금액이 정확히 1회 반영 |
| DEL-06 | 완료 상태와 화물 적재 목록, HUD, 미니맵을 함께 갱신한다. | 배송 수 증가, 완료 표시, 후속 손상 계산 제외 |

#### 배송 판정 방식 (초기 구현안)

- `DELIVERING` 중이며 배송 이벤트 시각이 전체 제한시간 이내일 때만 배송할 수 있다.
- 미배송 집의 배송 구역 안에서는 속도와 관계없이 Space 안내를 표시하고, 새 Space 입력 시 배송한다. 전진·후진 모두 동일하다.
- 사용자 수정 요청에 따라 정차·속도 조건을 제거한다. 이동·충돌·화물 손상 갱신 후 현재 위치로 배송을 판정한다.
- Space가 새로 눌린 순간에만 배송하며, 키를 계속 누른 상태로 구역에 진입해도 배송하지 않는다.
- 배송 구역이 겹치면 가장 가까운 미배송 집 하나만 대상으로 선택한다. 거리가 같으면 집 ID 순으로 선택한다.
- 배송 직후 집·화물 완료 상태를 변경해 중복 배송·정산을 방지한다.

배송 구역 크기는 실제 조작 테스트로 조정한다.

### 5.5 고객 기분과 정산

모든 집의 마감은 개별 집을 향해 출발한 시간이 아닌, 스테이지 출발 시점부터의 경과시간으로 계산한다.

| 고객 기분 | 배송 시점 `t`와 집별 마감 `deadline` | 배율 |
| --- | --- | --- |
| 만족 | `t <= deadline × 0.7` | 1.2 |
| 보통 | `deadline × 0.7 < t <= deadline` | 1.0 |
| 불만 | `t > deadline` | 0.7 |

```text
내구도 비율 = 배송 시 현재 내구도 / 최대 내구도
건별 최종 배달비 = floor(기본 배달비 × 고객 기분 배율 × 내구도 비율)
누적 수익 = 완료된 모든 배송의 건별 최종 배달비 합
```

원 미만 버림은 중간 계산 없이 각 배송의 최종 금액에서 한 번만 적용한다. 집별 마감이 지나도 배송은 가능하며 불만 배율을 적용한다. 전체 제한시간과 집별 마감을 별도 관리한다.

예시: B집 기본비 550원, 만족, 내구도 73%이면 `floor(550 × 1.2 × 0.73) = 481원`이다.

### 5.6 월드와 카메라

- 전체 월드는 플레이 화면보다 넓게 구성하고 오토바이 중심으로 카메라를 이동시킨다.
- 집을 서로 떨어뜨려 배치하고 여러 도로와 골목으로 경로 선택을 제공한다.
- 월드 좌표와 화면 좌표를 구분하고 충돌·배송·NPC는 일관된 월드 좌표를 사용한다.
- 미니맵으로 화면 밖 배송지와 현재 위치를 확인할 수 있게 한다.
- 월드 크기, 도로 폭, 집·출발지 위치는 실제 주행으로 조정한다.

넓은 월드와 추적 카메라는 원문에서 새 설계 제안으로 제시되었고 이후 개발 일정에 포함되어 있다. 화면 대비 월드 크기 3~4배는 확정 수치가 아니다. 실제 그래픽은 참고 이미지의 가독성 요소를 활용해 별도로 제작한다.

**사용자 UI 참고 이미지 반영:** 화면에는 큰 월드의 일부만 표시한다. 오토바이가 아래쪽으로 이동하면 카메라도 아래쪽으로 따라가며 새로운 맵 영역이 보인다. 위·좌·우 이동에도 같은 추적 규칙을 적용한다. 화면 단위로 맵을 교체하지 않고 연속 스크롤한다. 맵 중앙에서는 플레이 영역 중심을 추적하고 맵 끝에서는 카메라만 멈춰 플레이어가 화면 가장자리로 이동한다. 플레이어의 월드 경계 제한은 별도로 처리한다.

**권장 수정안:** 단계 간 맵 크기 1.2배·1.4배는 월드의 가로·세로 길이를 각각 확대한 비율로 정의한다. 따라서 면적은 각각 1.44배·1.96배다. 이 기준은 원문에 없던 해석을 명시한 초기안이며, 실제 이동 거리와 난이도를 확인해 조정한다.

#### pico2d 기반 카메라 처리 (구현 권장)

현재 HUD 적용 배치: 창은 1280×720, 플레이 뷰포트는 왼쪽 1000×720, 오른쪽 배송 마감 패널은 280픽셀이다. 상단의 얕은 정보 바와 하단 화물 내구도 패널을 사용하고, 집별 마감·고객 기분은 오른쪽 패널에 표시한다. 원형 미니맵은 플레이 뷰포트 오른쪽 위에서 상단 바 아래에 두며, 지도 내부 축척은 유지하고 원의 외곽 여백을 줄인다. 화면 좌표 HUD는 카메라 추적·월드 좌표 계산과 분리한다.

카메라 위치 `(camera_x, camera_y)`는 플레이 뷰포트에 보이는 월드 영역의 왼쪽 아래 좌표로 정의한다. 플레이 뷰포트는 창에서 오른쪽 마감 패널을 제외한 영역이다. 플레이어를 뷰포트 중앙에 두는 위치를 계산한 뒤 맵 경계로 제한한다. 초기에는 즉시 추적하며 보간·지연 효과는 필수로 추가하지 않는다.

```text
camera_x = clamp(player_x - viewport_width / 2, 0, max(0, world_width - viewport_width))
camera_y = clamp(player_y - viewport_height / 2, 0, max(0, world_height - viewport_height))
screen_x = viewport_left + world_x - camera_x
screen_y = viewport_bottom + world_y - camera_y
```

맵 중앙에서는 카메라가 플레이어를 따라가고, 가장자리에서는 카메라 이동을 제한한다. 월드 객체는 카메라 변환 후 출력한다. HUD는 고정 화면 좌표를 사용하고, 미니맵은 월드 좌표를 미니맵 영역으로 별도 축소 변환하므로 카메라 이동의 영향을 받지 않는다. 충돌·배송 판정은 화면 좌표가 아닌 월드 좌표를 사용한다.

월드 출력은 플레이 뷰포트 안으로 제한해 오른쪽 패널을 침범하지 않게 한다. 뷰포트 위치·크기와 패널 폭은 설정으로 관리한다. 패널 구현 전에는 창 전체를 임시 뷰포트로 사용할 수 있다. 월드가 뷰포트보다 작은 축은 카메라 좌표를 0으로 유지한다.

#### NPC 차량과 신호등 동작 방식 (구현 권장)

NPC 차량은 지정 경로점을 따라 이동하고 교차로에서 다음 경로점 방향으로 회전한다. 신호등이 있는 교차로에서는 연결된 신호를 확인해 적색이면 정지선 앞에 정차하고 녹색이면 재출발한다. 이미 교차로에 진입한 차량은 다음 구간까지 빠져나가도록 구성한다.

경로 마지막 지점은 처음 지점으로 연결해 반복 이동한다. 마지막 위치에서 처음 위치로 순간 이동시키지 않고 연결 구간을 주행할 수 있도록 도로와 경로를 배치한다. 차량 수와 속도는 스테이지 설정으로 관리한다.

보행자는 횡단보도의 지정 경로를 이동하며 플레이어 접촉을 별도로 판정한다. 접촉 페널티는 밸런스 테스트 후 결정한다. 배송 중 플레이어의 적색 신호 위반에는 건당 100원 벌금을 부과한다. 상세 판정은 추가 신호 위반 규칙을 따른다. 실제 차량·장애물 충돌에는 충돌 규칙을 적용한다.

- [v1.5 변경] 1단계부터 적용한다. 화물 수령을 이벤트 시계의 `t = 0`으로 정하고 수령 대기 중에는 발생시키지 않는다. 첫 예고까지의 대기와 각 묶음의 **예고 시작부터 다음 예고 시작까지**의 간격을 매번 9~11초 범위에서 균등 추첨한다. 첫 발생도 10초로 고정하지 않는다.

- [v1.5 보완 초기안] 개별 낙하 소요 시간은 예고 시작 전에 확정한다. 위험 영역 안에 좁혀드는 동심원을 표시하며, 전체 예고 시간 `2초 + 개별 낙하 시간`을 기준으로 원이 줄어들어 **실제 착지 순간에 중심에 도달**하게 한다. 2초 사전 경고가 끝나도 동심원은 초기화하거나 없애지 않고 낙하 중 계속 진행한다. 고정된 바깥 테두리는 실제 위험 범위를 끝까지 표시해, 줄어드는 원을 안전 범위로 오해하지 않게 한다.
- 운석의 표시 높이는 시각 효과이며 실제 충돌은 지상의 예고 좌표에서만 발생한다. 카메라가 이동해도 낙하 목표 월드 좌표는 바뀌지 않는다.

#### 랜덤 위치와 차단 크기 [v1.8 변경]

- [v1.8 변경] 맵 내부를 후보로 사용하고 크레이터 전체가 월드 경계 안에 들어오는 위치만 채택한다. 도로 밖도 허용하되 집·건물의 전체 표시 영역과 기존 고정 장애물 충돌 영역을 제외한다. 배달소 수령·복귀 구역 및 모든 집별 배송 구역은 오토바이 충돌 반경의 1.1배 접근 여유까지 보호한다. 이동·정지 중인 자동차와 보행자의 현재 충돌 영역과 겹치는 후보도 제외한다. 경고 후에는 목표를 고정하며 플레이어를 추적하지 않는다. 선정 뒤 NPC가 진입할 수 있으므로 착지 직전 겹침 검사도 유지한다.

- [v1.5 변경] 묶음당 근처 우선 배정 수를 2개 또는 3개로 동일 확률 추첨한다. 예고 시작 시점 플레이어 위치·방향과 카메라를 기준으로 **현재 플레이 영역에 보이는 전방 도로**의 유효 후보를 우선 선정한다. 전방은 실제 이동 방향을 기준으로 하며 후진 중에는 뒤쪽, 정지 중에는 차체가 향한 방향으로 정한다. 전방 후보가 부족하면 현재 카메라의 플레이 영역 안에 있는 다른 도로로 넓힌다. 이 후보 정의는 [v1.5 보완 초기안]이다.
- [v1.8 변경] 근처 도로 우선 배정 후 나머지는 도로 밖도 포함한 전체 맵의 안전한 후보에서 중복 없이 추첨한다. 현재 플레이어 위치 자체는 자동 낙하 후보의 제외 조건으로 삼지 않으며 경고로 회피 시간을 보장한다. 수동 생성에서는 착지 처리 없이 즉시 장애물이 생기므로 오토바이와의 겹침도 금지한다. 모든 후보는 건물·고정 장애물·NPC·배송 접근 보호 조건을 지킨다. 근처 후보가 부족하면 전체 맵에서 보충하고 로그를 남기되 안전 조건은 해제하지 않는다.

- [v1.7 대체] 탈출 경로는 **오토바이 지름과 안전 여유를 확보한 연속 통행 공간**이며, 아래 도로 연결성 검사로 판정한다. 반경 4배만큼 움직일 수 있다는 이유로 탈출 가능하다고 판정하지 않는다. 출발점이 위험 영역 안이면 출발점과 겹친 영역에서 나오는 최초 구간만 허용하며, 다른 위험 영역을 가로지르거나 같은 영역에 재진입하는 경로는 인정하지 않는다. 탈출 검사는 피할 공간과 연결 경로의 존재를 보장하며, 모든 속도·조향·입력에서의 무피격을 보장하지 않는다.
- 탈출 경로를 막는 후보는 제외하고 다시 선정한다. 정해진 후보 목록을 모두 확인해도 조건을 만족하지 못하면 근처 우선 수량을 줄이고, 전체 맵 보충 후보도 같은 검사를 통과해야 한다. 그래도 불가능하면 해당 묶음 수량을 줄이거나 생성을 건너뛰고 이유를 로그에 남긴다. [v2.2 변경] 20~24개 수량이나 근처 2~3개를 맞추기 위해 탈출 조건을 해제하지 않는다. 예고 후 플레이어의 자발적 이동까지 추적하여 낙하 지점을 변경하지 않는다.
- 후보 탐색은 무한 반복하지 않는다. [v2.2 변경] 유효 후보가 요청한 20~24곳보다 적으면 가능한 수에 대해 탈출 검사를 통과한 경우만 생성하고 부족 수량을 기록한다. **정상 맵 인수 기준은 배치와 탈출 조건을 만족하는 24곳 이상을 확보할 수 있는 대표 주행 위치 확인**이며, 수량 부족을 건물·배송 접근 보호 조건 위반으로 보충하지 않는다.

#### [v1.7 추가] 공통 도로 판정과 탈출 탐색 기준

- [v1.8 변경] 도로 렌더링, 근처 도로 후보 분류와 도로 탈출 경로 검사는 **동일한 맵 도로 형상 데이터**를 기준으로 한다. 도로 밖은 낙하 허용 영역이지만 도로로 분류하지 않는다. 직선·곡선·교차로·막다른 길을 포함하며 보도·노면 장식은 도로 형상에 추가하지 않는다. 화면 색상이나 곡선 외접 사각형, 미니맵 축소 도형으로 실제 도로를 판정하지 않는다.
- 도로 내부 여부는 중심점뿐 아니라 대상 원 전체가 도로 영역의 **합집합 안에 포함되는지** 검사한다. 도로 타일 경계를 넘는 원도 합집합에 포함되면 허용한다. [v1.8 변경] 이 기능은 도로 분류와 도로 경로 검사에 유지하며, 운석의 도로 밖 배치를 거부하는 조건으로 사용하지 않는다. 원 전체의 월드 내부 여부와 건물·배송 접근 보호는 별도의 공통 배치 제한으로 판정한다.
- [v1.8 후속 구현 기준] 도로 밖에서 피격되었을 때 밀어내기는 도로로 순간 이동시키지 않고 현재 위치에서 연결된 안전한 통행 가능 지면으로 짧게 보정한다. 기존 벽 통과 금지·거리 상한·다른 위험 영역 제외·보정 불가 시 착지 취소는 유지한다. 도로 밖 자동 후보의 탈출 검사도 안전 지면에서 기존 도로 통로로 이어지는 경로를 확인하도록 확장한다. 이 연결성 검사와 실제 착지 보정은 해당 개발 단계에서 구현한다.
- [보완 초기안] 맵 로딩 시 도로 중심선의 연결 그래프를 준비하고, 운석을 고려하지 않은 상태에서 오토바이 폭으로 통행 가능한 **교차로 노드 또는 다음 도로 구간으로 이어지는 타일 경계의 통로**를 탈출 목표 후보로 등록한다. 탈출 목표는 플레이어 시작점에서 직선거리 `오토바이 충돌 반경 × 4` 이상 떨어진 곳이어야 한다. 고정 장애물로 막힌 통로는 등록하지 않는다.
- 묶음 선정 시 현재 위치에서 **모든 위험 영역 밖에 있는 탈출 목표까지 연결되는 경로**를 하나 이상 확인한다. 목표에 닿는 것뿐 아니라 목표에서 이어지는 도로 구간으로 오토바이 지름 이상 더 진행할 수 있어야 한다. 작은 빈 공간 안에서만 맴도는 경로나 위험 원 바로 바깥의 한 점은 탈출로 인정하지 않는다. 이는 도로망 전체나 모든 배송지까지의 연결을 보장하는 조건은 아니며, 일시 차단은 3초 후 해제된다.
- [보완 초기안] 경로 탐색은 간격 `오토바이 충돌 반경 / 2` 이하의 도로 격자 또는 동등한 정확도의 연결 그래프를 사용한다. 모든 연결 구간은 오토바이 원 전체의 이동 경로로 검사한다. 대각선 이동으로 막힌 모서리를 통과할 수 없으며, 그래프 연결선이 벽이나 위험 영역을 가로지르면 그 연결을 사용하지 않는다. 도로 내부 근사 오차가 불확실하면 통행 불가로 판단한다.
- [보완 초기안] 묶음 하나의 후보 평가 상한은 **500회**, 경로 검사 호출 상한은 **20회**, 묶음 전체 경로 탐색 노드 확장 합계 상한은 **20,000개**로 둔다. 각 경로 호출은 남은 합계 예산 안에서 수행한다. 밀어내기 도착점 탐색은 객체당 **64개 후보**까지 검사한다. 이 값은 설정으로 관리하며, 후보 교체·수량 축소 재검사도 같은 묶음 예산에 포함해 무한 재시도하지 않는다.
- 예산 초과는 ‘안전 확인 불가’이며 통과로 간주하지 않는다. 아직 예산이 남았다면 후보 제거·수량 축소 후 재검사하고, 예산이 소진되면 미확정 묶음을 생략한다. 밀어내기는 탐색 상한 안에서 안전 위치를 찾지 못하면 해당 착지를 취소한다. 정상 도로 데이터와 고정 장애물 정보는 재사용하고, 매 프레임 도로 그래프 전체를 다시 만들지 않는다.
- 개발 로그에는 후보 부족·탈출 불가·탐색 한도 초과·안전 위치 부족을 구분하고 묶음 ID, 최종 수량, 검사 횟수, 탐색 노드 수, 처리 시간을 기록한다. 같은 난수 시드로 동일한 배치를 재현할 수 있도록 개발용 시드 설정을 제공한다. 실제 실행 환경에서 주기 발생 시 눈에 띄는 멈춤이 없는지 측정하며, 한도 조정으로 안전 조건을 생략하지 않는다.

#### [v1.7 추가] 원형 크레이터 충돌 기준

- 오토바이와 크레이터는 각각 원으로 판정한다. 중심 거리와 두 충돌 반경 합을 비교하며, 경계 접촉은 통행 차단으로 처리한다. 표시된 크레이터 위험 범위와 실제 충돌 반경은 일치시킨다. 원을 둘러싼 사각형으로 최종 충돌을 대체하지 않는다.
- 고속 주행과 큰 프레임 이동에서도 원형 크레이터를 관통하지 않도록 **이전 위치부터 목표 위치까지 움직이는 원의 경로**를 검사한다. 사각형 고정 장애물과 원형 크레이터를 함께 고려하여 가장 먼저 막히는 위치까지만 이동하고, 가능한 접선 방향 이동을 허용한다. 최종 위치는 두 종류 장애물과 맵 경계를 모두 만족해야 한다. 착지에 의한 초기 겹침은 앞서 정한 안전 보정·취소 규칙으로 처리한다.
- 접촉 기록은 목록 순번이 아닌 **삭제되어도 다른 객체에 재사용되지 않는 장애물 ID**로 관리한다. 크레이터 해제 시 해당 ID의 접촉 기록도 제거한다. 다른 크레이터의 제거 때문에 유지 접촉이 새 충돌로 바뀌거나 새 충돌이 누락되어서는 안 된다. 통행 판정용 미세 오차 허용값과 접촉 유지 여유는 공통 설정으로 일관되게 적용한다.
- 원형 차단·착지·해제와 표시 갱신은 같은 시뮬레이션 상태를 사용한다. 프레임 지연 중 이미 끝난 차단을 추가 3초 연장하거나, 남아 있어야 할 차단을 표시만 제거하지 않는다. 신규 묶음의 경고 시간을 보장하는 지연 예외와 기존 운석의 상태 경과 처리는 구분한다.

#### 착지, 통행 차단과 피해 [보완 초기안]

- 상태는 `WARNING(예고) → FALLING(낙하) → BLOCKED(착지·차단) → REMOVED(해제)`로 진행한다. 예고·낙하 중에는 통행 가능하고, 착지 순간부터 원형 크레이터를 임시 고정 충돌체로 등록한다.
- 착지 순간 오토바이 원과 크레이터 원이 겹치면 오토바이 속도를 0으로 만들고, 적재 중인 각 화물에 **최대 내구도의 10% × 종류별 충돌 직접 피해 배율**만큼 1회 피해를 준다. 정지해 있어도 착지 피해가 발생하며, 기존 상대 속도 공식으로 낙하 피해를 계산하지 않는다. 내구도는 0 미만으로 내려가지 않는다.
- [v1.5 강화] 새 크레이터가 오토바이 아래 생기면 기존 장애물·모든 크레이터·맵 경계뿐 아니라 **현재 경고·낙하 중인 모든 위험 영역과 NPC 충돌 영역**을 피하는 가장 가까운 유효 도로 위치로 밀어낸다. 오토바이 중심만이 아니라 충돌 원 전체와 작은 안전 여유를 고려한다. 안전 여유 초기값은 오토바이 충돌 반경의 10%로 하여 크레이터 경계선 위에 배치하지 않는다. 같은 프레임의 다른 착지와 먼저 보정된 객체 위치도 반영한다. 유효 위치를 확보할 수 없는 낙하는 **착지 직전 취소**하며, 경고 표시도 함께 제거한다. 안전을 위한 예외로 수량이 줄어든 경우 로그를 남긴다.
- [v1.6 강화] 밀어내기 도착점은 **현재 위치에서 벽을 넘지 않고 도달할 수 있는 같은 국소 도로 구역**으로 제한한다. 가까워도 건물·담장 반대편 도로는 선택하지 않는다. [보완 초기안] 보정 거리 상한은 `크레이터 반경 + 해당 객체 충돌 반경 + 안전 여유`로 한다. 현재 위치부터 도착점까지 충돌 원 전체가 이동하는 직선 경로를 검사하여, 건물·기존 크레이터·NPC·맵 경계를 가로지르는 보정은 금지한다. 새로 착지할 해당 크레이터에서 빠져나오는 구간만 예외로 허용하고 다른 예고·낙하 영역으로 들어가는 보정은 금지한다. 이 조건을 만족하는 짧은 보정이 없으면 해당 낙하를 취소한다. 같은 제한을 NPC 보정에도 적용한다.
- [v1.6 추가] 개별 착지는 **착지 가능 여부 검사 → 겹친 객체 모두의 안전 위치 확보 → 착지 확정 → 충돌체 등록 및 피해·정지·밀어내기 적용** 순서로 처리한다. 안전 위치 탐색은 확정 전 계산으로만 수행하며, 겹친 객체 하나라도 보정 불가능하면 해당 낙하 전체를 취소한다. 취소 시 피해·감속·밀어내기·크레이터를 적용하지 않고 예고·운석·미니맵 마커를 제거한다. 안전 위치를 먼저 찾은 다른 객체도 취소된 낙하 때문에 이동시키지 않는다.
- [v1.6 보완 초기안] 한 프레임에 여러 착지가 예정되면 **예정 착지 시각 오름차순 → 동률일 때 생성 ID 오름차순**으로 처리한다. 각 착지의 안전 검사는 앞에서 확정된 충돌체와 보정 위치, 아직 처리 전인 경고·낙하 영역을 포함한다. 객체별 보정 도착점도 서로 겹치지 않게 확보한다. 앞선 착지가 취소되면 그 착지의 임시 예약은 해제한 뒤 다음 착지를 검사한다. 확정 전에는 피해를 주지 않아 취소 후 내구도·위치를 되돌리는 처리가 필요하지 않게 한다.
- [v1.5 보완 초기안] 밀어내기 직후 시뮬레이션 시간 기준 **0.2초 동안 크레이터의 추가 접촉 피해·감속을 유예**한다. 통행 차단과 겹침 방지 위치 보정은 계속 적용하여 크레이터 관통을 허용하지 않는다. 다른 운석의 착지 피해나 일반 장애물 충돌까지 무적으로 만들지 않는다. 유예가 끝나도 접촉 유지 중인 크레이터를 새 접촉으로 간주하지 않으며, 이탈 후 재접촉해야 추가 피해를 준다.
- 착지 피해와 같은 크레이터의 첫 접촉 피해를 중복 적용하지 않는다. 이후 주행 중 크레이터 가장자리에 새로 충돌하면 5.3의 고정 장애물 충돌 규칙을 적용하며, 접촉 유지 중에는 피해를 반복하지 않는다.
- 각 착지에서 3초가 경과하면 충돌체·크레이터·표지판·미니맵 표시를 함께 제거한다. 표시는 남았는데 통과되거나 표시 없이 막히는 상태를 허용하지 않는다. 초기안에서는 별도의 잔흔 유지 시간을 두지 않는다.
- 운석 착지와 배송 입력이 같은 프레임이면 **운석 상태 전환·착지 처리 → 이동 및 충돌 처리 → 화물 상태 갱신 → 배송·정산 → 성공·실패 판정** 순서를 적용한다. 4.3의 기본 판정 순서에 운석 처리를 앞에 추가하며, 감소한 내구도로 정산한다.
- 향후 자동차 NPC·보행자도 차단 영역을 통과하지 않고 앞에서 정지했다가 해제 후 기존 경로를 재개한다. 착지 때 겹친 NPC는 플레이어와 동일한 안전 제외 영역·안전 여유를 적용해 유효 위치로 보정하며, 유효 위치가 없으면 해당 낙하를 취소한다. NPC 체력·운석 피해 시스템은 이번 범위에 추가하지 않는다.
- [v1.5 추가] NPC는 차단 구역 또는 같은 경로의 앞차와 안전거리를 유지하며 대기한다. [보완 초기안] 차체 경계 사이 최소 간격은 뒤차 충돌 반경의 0.5배로 하고, 그 간격과 현재 속도에서의 제동거리를 확보하도록 미리 감속한다. 해제 후에는 선두부터 이동하고 뒤차는 안전거리가 확보될 때 출발한다. 재출발과 위치 보정으로 객체가 겹치지 않아야 하며, 앞차·보행자가 떠난 뒤에도 이전 차단 상태 때문에 영구 대기하지 않도록 매 프레임 진행 가능 여부를 다시 판단한다.

#### 게임 화면과 미니맵 [보완 초기안]

| 상태 | 게임 월드 표시 | 미니맵 표시 |
| --- | --- | --- |
| 예고 | 위험 범위의 고정 붉은 테두리와 실제 착지 시각을 향해 좁혀드는 동심원. 기존 배송 구역과 구분한다. | 같은 월드 위치에 빨간 테두리 원 |
| 낙하 | 고정 위험 테두리·동심원을 유지하고 그 위로 내려오는 운석을 표시한다. | 빨간 테두리 원의 깜빡임 유지 |
| 차단 | 크레이터 자국과 충돌 범위를 표시하고, 위에 이동 불가 표지판 및 해제까지 남은 초를 띄운다. | [v1.5 보완] 고정 빨간 외곽선 안의 채움 원이 남은 시간에 비례해 축소 |

- 미니맵 마커는 월드 위치를 기존 지도 축척으로 변환하고 원형 미니맵 경계 밖으로 그리지 않는다. 플레이어·배송지 마커가 운석 마커에 완전히 가려지지 않도록 우선 표시한다.
- [v1.5 보완 초기안] 미니맵은 투명도 변화 대신 **채움 원 축소 방식**을 채택한다. 채움 반경은 `기본 마커 반경 × clamp(남은 차단 시간 / 3초, 0, 1)`로 계산한다. 바깥 빨간 테두리는 차단 종료까지 유지해 작은 채움 원을 실제 차단 범위 축소로 오해하지 않게 한다. 예고는 깜빡이는 빈 원, 차단은 깜빡이지 않는 외곽선과 줄어드는 채움으로 구분한다. 해제 순간 외곽선도 함께 제거한다.
- 매 묶음 시작 때 고정 UI에 ‘운석 주의보’를 잠깐 표시한다. 낙하 중인 운석은 높이 표현을 사용하되 HUD와 오른쪽 정보 패널을 침범하지 않도록 플레이 영역에 클리핑한다.

#### 게임 상태 및 밸런스 [보완 초기안]

- 이벤트 시계는 프레임 수가 아닌 시뮬레이션 `dt`로 진행한다. 일시정지 시 예고·낙하·차단 시간과 애니메이션을 모두 멈춘다. 복귀 시 배송 타이머와 혼동하지 않도록 운석 시계를 별도로 관리한다.

- 큰 `dt`로 예정 시각을 넘긴 경우 누락 묶음을 한 프레임에 몰아서 생성하지 않고 현재 시점에서 묶음 하나만 새로 예고한다. 이때도 최소 2초 경고를 보장하고 다음 예고는 해당 예고 시작에서 새로 추첨한 9~11초 뒤로 잡는다.

#### [v1.9 추가] 3단계 수동 확인 범위

- F1 디버그 모드에서 F3으로 ‘크레이터’와 ‘운석’ 도구를 전환한다. 크레이터 도구의 좌클릭은 랜덤 크기의 충돌체를 즉시 생성하고, 운석 도구의 좌클릭은 한 개의 예고·낙하 확인을 시작한다. 운석은 한 번에 한 개만 진행한다. 우클릭은 지상 목표 영역의 운석 취소 또는 크레이터 삭제, F2는 전체 삭제다.
- 운석은 고정 외곽 원과 실제 착지까지 줄어드는 동심원·잔여 시간 표시를 사용한다. 2초 뒤 위에서 수직 낙하하고, 시작 전에 추첨한 0.6~1.4초 후 착지 시점에 도달한다. 카메라가 움직여도 목표 월드 좌표를 유지하고 도형은 플레이 뷰포트에 잘라 그린다. F1을 꺼도 기존 운석 연출은 계속 진행한다.
- 이번 단계는 **시각 예고와 낙하까지**다. 예고·낙하 운석에는 충돌이 없으며 착지 시점에 연출을 종료한다. 착지 피해·밀어내기·크레이터 전환·3초 해제는 4단계, 주기적 묶음 생성·미니맵·첫 안내는 이후 단계에서 연결한다. 임시 도구임을 F1 안내에 표시한다.
- 일시정지·결과에서는 연출 시간을 멈추고, 재시작 시 임시 운석도 제거한다. 별도 테스트 실행과 실제 플레이 확인은 사용자가 수행한다.

#### [v2.0 추가] 4단계 수동 확인 범위와 처리 기준

- F1 → F3 운석 도구 → 좌클릭으로 예고·낙하를 시작한다. 생성 시 오토바이와 겹치는 위치는 계속 거부하지만, 예고 후 플레이어가 위험 원에 진입하는 것은 허용한다. 착지 순간 오토바이 충돌 원이 위험 원과 접촉·중첩하면 피격으로 처리한다. 경고·낙하 중 운석 자체는 지상 충돌을 발생시키지 않는다.
- 착지 직전에 건물 표시 영역·고정 장애물·배송 접근 보호·기존 크레이터 겹침을 다시 검사한다. 피격 예정이면 최대 64개 방향의 짧은 직선 보정 후보를 거리순으로 검사한다. 도착점은 오토바이 반경과 10% 안전 여유까지 확보하고, 도착점과 이동 경로는 건물·기존 크레이터·맵 경계를 피한다. 도로 밖에서는 안전한 통행 가능 지면으로 보정할 수 있으며, 새 크레이터를 빠져나오는 구간만 허용한다. 다른 예고·낙하 영역을 제외하는 탐색 입력을 준비하며 현재는 단일 운석이라 다른 운석이 없다.
- 안전 위치를 확보하기 전에는 속도·위치·화물을 변경하지 않는다. 배치 또는 안전 보정이 불가능하면 운석을 취소하고 모든 객체의 위치·속도·화물 내구도를 그대로 유지한다. 취소 이유는 디버그 안내와 개발 로그에 표시한다.
- 확정된 착지는 오토바이를 안전 위치로 보정하고 속도를 0으로 만든다. 배송 중에만 미배송·미파손 화물마다 `최대 내구도 × 0.10 × 종류별 충돌 직접 피해 배율`의 피해를 한 번 적용한다. 복귀 중에는 보정·정지·차단만 적용하고 화물·수익·배송 시계는 바꾸지 않는다. 기존 흔들림 손상은 별도 규칙으로 계속 처리한다.
- 밀어내기 직후 0.2초 동안 모든 크레이터의 추가 접촉 피해·감속만 유예한다. 통행 차단은 유지하고 건물 충돌·새 운석 착지 피해는 정상 적용한다. 착지 접촉을 미리 소비하고 유예 중 접촉도 기록하여, 유예 종료 시 접촉 유지 때문에 새 피해를 주지 않는다.
- 크레이터의 반경은 해당 운석의 34~54픽셀 추첨값을 유지한다. 착지 시각부터 3초 동안 충돌체와 이동 불가 표지·잔여 시간 표시를 유지하고 같은 프레임에 제거한다. 큰 프레임 경과가 있으면 착지 예정 시각 이후의 경과분을 차단 잔여 시간에서도 빼며, 무조건 추가 3초를 부여하지 않는다.
- F3의 **즉시 크레이터 도구**는 반복 접촉 확인을 위해 수동 삭제까지 유지한다. **운석이 만든 크레이터**만 이번 단계의 3초 자동 해제를 사용한다. 우클릭과 F2는 두 종류 모두 삭제하고 접촉·해제 예약도 함께 정리한다. 일시정지·결과에서는 운석과 해제 시계를 멈추며 재시작 시 모두 초기화한다.
- 처리 순서는 운석 착지·해제 → 보정 이후 위치에서 주행 → 건물·크레이터 이동 충돌 → 화물 흔들림 갱신 → 배송·정산 → 성공·실패 판정이다. 같은 프레임 배송에는 착지 피해가 반영된 내구도를 사용한다. 주기적 여러 운석·포위 방지 묶음 검사·미니맵 표시는 후속 단계다.

#### [v2.1 추가] 5단계 묶음 발생 구현 범위

- 화물 수령에 성공한 순간 자동 주기를 한 번 시작한다. 수령 전에는 수동 확인 도구만 동작한다. 첫 예고까지 9~11초를 추첨하고, 각 묶음 예고가 실제 시작된 시각부터 다음 예고까지 다시 9~11초를 추첨한다. 수령 대기 시간은 자동 발생의 첫 대기에 합산하지 않는다.
- 묶음 수량은 9개 또는 10개를 같은 확률로 추첨한다. 도로 밖을 포함한 맵 내부에서 후보를 추첨하고, 기존 건물 표시 영역·고정 장애물·모든 배송/수령/복귀 접근 여유·기존 크레이터·모든 예고/낙하 영역·같은 묶음의 확정 후보와 겹치면 거부한다. 자동 운석 후보는 현재 플레이어 위치를 추적하거나 제외하지 않으며 회피 시간은 사전 경고로 제공한다. 즉시 생성하는 수동 도구는 기존처럼 오토바이와의 겹침을 거부한다.

- 각 운석 반경은 34~54픽셀이다. 묶음 시작 전에 개별 낙하 시간을 0.6~1.4초 범위의 밀리초 값 중 중복 없이 추첨한다. 위치·반경·낙하 시간을 모두 확정한 뒤 같은 시각에 2초 예고를 시작하므로 묶음 내 예고와 낙하 시작이 동기화되며 착지는 개별 시간에 따른다.
- 운석마다 프로세스 내 재사용하지 않는 생성 ID와 묶음 번호, 예고 시작 시각을 가진다. 수동 운석의 묶음 번호는 없음으로 구분한다. 한 프레임의 착지 사건은 예정 착지 시각·생성 ID 순으로 처리하고, 각 사건 시점에 먼저 만료된 크레이터를 해제한다. 앞선 보정 위치와 확정 크레이터는 뒤 사건에 반영한다.
- 안전 밀어내기에는 현재 운석을 제외한 모든 예고·낙하 영역을 전달한다. 아직 처리 전인 같은 프레임의 착지 예정 운석도 위험 영역으로 포함하고, 도착점뿐 아니라 보정 경로가 다른 위험 영역을 통과하는 경우도 거부한다. 취소한 운석은 이후 사건의 위험 영역에서 제거한다. 안전 위치를 못 찾으면 기존 규칙대로 피해 없이 취소한다.
- 지연 프레임에서 새 묶음은 최대 하나만 현재 시각에 생성하고, 새 예고에 이미 경과한 프레임 시간을 적용하지 않는다. 다음 예정 시각도 현재 예고 시작부터 새 간격으로 잡는다. 기존 운석의 착지·해제는 원래 예정 시각으로 처리하여 차단 3초를 추가 연장하지 않는다.
- 복귀·실패·클리어 판정 즉시 자동 주기를 중단한다. 복귀 중 기존 운석은 종료까지 진행하되 화물 피해는 없고, 결과에서는 운석 시뮬레이션 자체가 정지한다. 일시정지 시 다음 묶음 대기·예고·낙하·해제 시간이 함께 멈춘다. 재시작은 관리자 전체를 새로 구성해 묶음 번호·다음 예정 시각·운석·충돌·접촉을 초기화한다.

#### [v2.2 추가] 6단계 배치·탈출 검사의 구체 기준

- `MIN_WAVE_COUNT=20`, `MAX_WAVE_COUNT=24`로 수량을 조절한다. 근처 요청 수는 2~3개로 유지한다. 예고 시작 시점의 카메라·플레이어 위치·차체 각도·속도 부호를 한 번 사용하며, 후진 시 차체 반대 방향, 정지 시 차체 방향을 전방으로 삼는다. 해당 묶음의 확정 위치를 이후 추적 변경하지 않는다.

- 근처 전방 후보 검사는 최대 160회, 화면 전체 도로 후보는 최대 120회이며, 두 단계·전체 맵 추첨·교체의 합계는 기존 묶음당 500회를 넘지 않는다. 정적 도로 격자 준비는 재사용 가능한 지도 분류이며, 실제 반경으로 평가한 후보 시도는 모두 500회 예산에 포함한다.
- 탈출 탐색 격자 간격은 오토바이 충돌 반경/2이고, 통행 폭은 오토바이 반경에 10% 여유를 더해 검사한다. 건물은 전체 표시 영역과 고정 장애물 충돌 영역을 함께 제외한다. 실제 연결 비트가 이어진 도로 타일 경계만 통로 후보로 등록하고, 시작점에서 오토바이 반경 4배 이상 떨어진 통로와 그 너머 오토바이 지름 이상의 진행 공간까지 확인한다.

#### [v2.3 추가] 7단계 표시·안내 구현 기준

- 미니맵은 운석 관리자의 현재 운석/크레이터 목록과 `crater_remaining()`을 직접 참조한다. 마커 수명이나 잔여 시간을 따로 복제하지 않는다. 예고·낙하 중에는 고정 지상 목표에 빨간 테두리 원을 표시하고 월드와 같은 점멸 상태를 사용한다. 카메라 이동이나 운석 표시 높이는 미니맵 목표 위치를 바꾸지 않는다.

| 수령 대기 | 배송 경과 0, 자동 주기 시작 안 함. 기존 F1 수동 확인용 운석만 운석 시계로 진행 가능 |
| 화물 수령 | 새 입력 1회로 수령하고 `WAITING → DELIVERING` 전환 시에만 자동 주기를 시작. 같은 상태 동기화·Space 반복으로 재시작하지 않음 |
| 배송 중 | 기존 착지·이동 충돌·화물 손상 후 내구도로 배송·정산. 한 요청은 마지막 하위 단계에서만 처리하고 실패해도 다음 프레임으로 넘기지 않음 |
| 복귀 중 | 자동 주기 즉시 중단. 진행 중 예고·낙하·크레이터는 원래 수명대로 종료. 이동 차단·감속·위치 보정만 허용하고 내구도·수익·배송 시계·실패 판정은 고정 |
| 실패·클리어 | 남은 시간 단계를 즉시 중단하고 운석·해제·점멸 시계 동결. 신규 생성·배송 불가, 경고음 정지 |
| 일시정지 | 모드 갱신과 운석 관리자 모두 정지 상태를 반영. 배송·주행·운석·주기·안내·효과음 함께 정지. 재개 유예 프레임에는 시뮬레이션과 배송 요청을 진행하지 않음 |
| 재시작·모드 종료 | 기존 효과음 정지·해제, 운석·크레이터·해제 예약·접촉·유예·주기·통계·지도 캐시·첫 안내 상태 제거. 주행 입력·보류 배송·일시정지 상태 정리. 재시작 전 유지 키는 해제 후 다시 눌러야 적용 |

- **마지막 배송과 발생 예정이 같은 프레임:** 기존 운석 사건과 손상을 먼저 처리하고 마지막 배송·정산을 수행한다. 성공 시 복귀 상태를 먼저 확정하여 예정된 새 묶음을 생성하지 않는다. 실패·클리어로 전환한 프레임도 신규 묶음을 생성하지 않는다. 기존 5단계의 ‘운석 갱신 안에서 바로 묶음 생성’ 방식은 폐기한다.
- **착지와 Space가 같은 프레임:** 처리된 모든 하위 단계의 착지·충돌·흔들림 손상을 반영한 최종 위치·내구도로 배송을 판단한다. 보정 후 구역 밖이면 배송되지 않는다. 착지 접촉과 일반 충돌 직접 피해는 중복 적용하지 않으며 일반 장애물 직접 피해·감속은 같은 렌더 프레임에서 한 번만 적용한다. 서로 다른 운석의 확정 착지 피해는 별도 사건이다.
- **제한시간 경계:** 프레임의 적용 시뮬레이션 시간을 기준으로 실제 배송 처리 시각이 `t <= 제한시간`이면 허용하고 `t > 제한시간`이면 거부한다. 표시 반올림이나 제한시간에 맞춘 강제 절단은 하지 않는다. 분할 때문에 시간이 누적 오차로 달라지지 않도록 같은 프레임 시작 경과에서 각 단계의 배송 시각을 계산한다. 정확한 경계에서 마지막 배송·수익 조건 충족 시 성공을 우선하고 이후 실패 검사는 생략한다.
- **판정 중간 실패:** 하위 단계에서 목표 수익 달성 불가 또는 시간 초과가 확정되면 이후 시간 단계·보류 배송을 버리고 결과를 유지한다. 조기 실패 상한·시간 초과·복귀 무실패의 기존 `GameController` 규칙은 변경하지 않는다.
- **장기 멈춤 처리 정책 [구현 보완 초기값]:** `game/config/simulation.py`의 `MAX_FRAME_TIME=0.25초`, `MAX_STEP_TIME=1/60초`를 사용한다. 한 렌더 프레임의 벽시계 경과 중 최대 0.25초를 게임 시간으로 적용하고, 초과 구간은 공통 정지 시간으로 취급해 버린다. 다음 프레임에 부채로 몰아 적용하지 않는다. 정상 범위 프레임은 전체 경과를 적용하며, 적용된 시간을 최대 1/60초 단위로 나눠 모든 객체·배송·손상·운석·주기를 같은 시간만큼 진행한다.
- 이 정책은 긴 창 이동·응답 지연 중 배송 시간만 흐르거나 운석만 즉시 착지하는 것을 방지한다. 게임 내 경고 2초·차단 3초·전체 제한시간 값은 그대로이고, 프로그램이 오래 멈춘 구간에는 벽시계보다 게임 시간이 적게 흐를 수 있다. 차단 해제 예약을 새로 3초로 덮어쓰지 않으며 같은 공통 시계의 착지 시각+3초를 유지한다. 실제 효과음은 전용 채널로 재생하고 명시적 일시정지·결과·종료에서 제어한다.
- 신규 묶음은 시간 분할이 모두 끝난 후 현재 위치·카메라·최종 상태로 한 번만 검사하고, 생성된 예고에는 이미 소비한 프레임 시간을 적용하지 않는다. 예정 시각이 지나도 밀린 묶음을 반복 생성하지 않는다. F1 상태에서 긴 프레임이 보정되면 실제/적용 시간을 로그에 남긴다.
- 운석 관리자 자체의 상태 가드는 호출자가 잘못 갱신해도 복귀 중 신규 발생, 결과/정지 중 시계 진행, 배송 외 착지 화물 피해를 막는다. F2의 현재 객체 삭제는 자동 주기 유지 동작이며, 재시작/종료 정리와 구분한다. 운석 ID의 프로세스 내 비재사용 정책은 유지한다.

#### [v2.4 성능 보완] 시간 분할 후 충돌 검사 비용

- 시간 분할 때문에 늘어나는 정밀 검사 비용을 줄이기 위해 이동 원의 경로 외접 상자와 겹치는 장애물만 정밀 충돌 검사한다. 겹침 보정 후에는 후보를 다시 선정하고, 최종 접촉도 여유 범위 안에서 조회해 관통 방지·접촉 ID 규칙을 유지한다.
- F1에 실제 벽시계 프레임 기준 FPS와 계산·그리기/화면 갱신 대기 시간을 표시한다. FPS 표시는 게임 시간 상한이나 하위 단계 수에서 계산하지 않는다. 성능 개선 정도는 실제 실행으로 확인하며 이번 작업에서는 테스트·플레이를 실행하지 않는다.
- 사용자 수동 측정에서 FPS 15.8, 계산 2.0ms, 그리기·대기 58.6ms가 관측되어 렌더링 경로를 추가 보완한다. 설치된 pico2d의 글자 출력은 매번 표면·텍스처를 생성하므로 HUD·미니맵·운석 문구·메뉴에 글자 텍스처 캐시를 적용한다. 폰트별 최대 256개 항목을 재사용하고 오래 사용하지 않은 항목부터 제거하며 재시작/종료 때 텍스처와 폰트를 해제한다. 글자 위치·색·게임 규칙은 유지한다.
- 병목을 더 구분할 수 있도록 F1의 그리기 실행 시간과 `update_canvas` 화면 갱신 대기를 별도로 표시한다. 개선 후 FPS와 두 시간은 사용자가 다시 확인한다.

### 6.2 스테이지 1: 확정 배송 데이터

현재 샘플의 무작위 배송 후보는 21채로, 기와집 3채·파란 주택 5채·상가 5채·카페 4채·아파트 4채다. 건물 종류에 관계없이 동일한 후보 목록에서 5채를 추첨한다. 추가 후보의 배송 구역은 주변 건물·소품과의 간격을 고려해 개별 설정하며, 배달소와 배송 구역이 없는 건물은 제외한다.

사용자 추가 요구에 따라 플레이 초기화마다 배송 구역이 정의된 후보 건물 중 5채를 중복 없이 무작위 선택한다. 배달소는 후보에서 제외한다. A~E는 이번 플레이의 배송 이름이며 아래 기본비·마감과 지정 화물을 선택된 건물에 순서대로 연결한다. 선택 결과는 해당 플레이 중 유지하고, 화물 수령이나 배송 시 다시 추첨하지 않는다. 무작위 추첨이므로 이전 실행과 일부 또는 전체 건물이 같을 가능성은 있다. 후보 건물의 위치·이미지·충돌 영역은 변경하지 않으며, 배송 구역은 건물별 오프셋과 크기로 관리한다.

위 최대 수익은 산술상 상한이며 실제 맵에서 모든 집을 만족으로 배송할 수 있다는 보장은 아니다. 단계가 높아질수록 화물 수·교통량·주행 부담이 증가하므로 수익 비율만으로 난이도를 판단하지 않는다.

각 단계에서 다음을 실제 플레이로 검증한다.

1. 모든 배송지를 제한시간 안에 방문하고 배송할 수 있는가.
2. 화물 손상을 최소화하는 안전 주행으로 목표 수익을 달성할 수 있는가.
3. 빠른 주행은 시간을 줄이면서 급회전·충돌에 따른 손상 위험을 높이는가.
4. 배송 순서에 따라 고객 기분과 최종 수익이 달라지는가.
5. NPC 차량·보행자가 통로를 영구 차단하거나 배송 진행을 불가능하게 만들지 않는가.

테스트에는 방문 순서, 배송 시각, 내구도, 건별·최종 수익, 충돌 및 막힘 상황을 기록한다. 시간·수익 목표를 동시에 충족하는 경로가 각 단계에 존재해야 한다. 초기안 수치는 결과에 따라 조정하되, 확정된 목표 수익·1단계 제한시간·핵심 규칙을 바꾸면 PRD와 상세 기획서에 변경 사항을 함께 반영한다.

| 집별 마감 패널 | 미배송 집의 남은 마감시간 및 경과 비율, 지각 시 초과시간과 붉은 느낌표 |
| 화물 상태 | 화물별 내구도·흔들림·미배송/완료 상태 |
| 미니맵 | 전체 지형, 플레이어 위치, 미배송 `!`, 완료 `✓`, 복귀 시 출발지 표시 |
| [v1.4 추가] 운석 안내 | 월드 사전 위험 원, 미니맵 빨간 예고·차단 마커, 크레이터·이동 불가 표지판·해제 카운트다운. 5.8 적용 |

| 실패 결과 | 실패 표시 및 재시작 제공 |

실패 사유를 시간 초과와 수익 달성 불가로 구분해 표시하는 것은 구현 권장이다. 원문의 HUD 수치는 예시이며 실제 게임 상태와 연결한다.

**화물 UI 권장안:** 최대 9개 화물을 고려해 미배송 화물의 내구도·흔들림을 우선 표시한다. 배송 완료 화물은 축소하거나 숨기되 전체 배송 완료 수는 유지한다. 선택한 해상도에서 마감 패널·미니맵·화물 목록이 겹치거나 잘리지 않는지 검증한다.

집별 UI 예시: 출발 후 48초에 A·B 배송을 마쳤다면 C는 42초, D는 67초, E는 92초가 남는다. A가 미배송이라면 3초 지각으로 표시한다. 복귀 중에는 배송 타이머와 수익이 계속 고정되어야 한다.

### 7.1 사용자 참고 이미지 기반 화면 배치

사용자가 제공한 UI 이미지를 배치와 가독성의 기준으로 사용한다. 이미지 속 수치·배송 완료 상태·색상별 의미는 예시이며 실제 게임 데이터로 대체한다. 최종 해상도와 각 영역의 픽셀 크기는 아직 확정하지 않는다.

#### 초기 개발용 크기 설정

`settings.py`에서 다음 값을 별도로 관리하고 실제 주행과 UI 확인 후 조절한다. 최종 제출 해상도나 확정 맵 크기를 의미하지 않는다.

| 설정 | 초기값 | 적용 범위 |
| --- | --- | --- |
| 창 크기 | 1280×720 픽셀 | 현재 실행 창 |
| 월드 크기 | 3600×2700 픽셀 | 사용자 도시 확장 요청에 따라 기존 2400×1800에서 확대. 현재 샘플 맵과 카메라 좌표가 참조하며 경계 제한은 별도 구현 |
| 오른쪽 배송 패널 폭 | 280 픽셀 | 향후 패널용 설정. 현재 영역을 비워 두거나 패널을 표시하지 않음 |
| 향후 플레이 영역 | 1000×720 픽셀 | 창 너비에서 배송 패널 폭을 뺀 값. 패널 도입 시 사용 |
| 현재 임시 플레이 뷰포트 | 왼쪽 아래 (0, 0), 1280×720 픽셀 | 패널 구현 전에는 창 전체 사용 |

현재 오토바이는 새 창 중앙인 (640, 360)에서 위쪽을 바라보며 시작한다. 창 크기를 바꾸면 실제 창 크기를 기준으로 시작 위치를 다시 계산한다. 이번 설정 단계에서는 카메라·미니맵·UI 패널·맵 경계 제한을 구현하지 않는다.

이후 샘플 도시 맵 적용 단계에서는 `data/maps/sample_map.json`의 출발 위치 (750, 450)를 사용하고 추적 카메라로 뷰포트 중앙에 표시한다. 도시 확장 샘플은 300픽셀 단위의 12열·9행 월드에 연결 도로 구간 15개, 건물 38채, 도시 소품 38개를 배치한 시각 확인용 데이터다. 카페·소형 아파트·분수를 포함하며 전봇대와 차량은 배치하지 않는다. 스테이지별 실제 배송 배치, 수령 기능, 충돌 처리를 확정하는 것은 아니다.

| 영역 | 배치 및 동작 |
| --- | --- |
| 메인 플레이 영역 | 창 왼쪽의 넓은 영역에 월드 일부를 표시하고 플레이어 이동에 따라 연속 스크롤 |
| 상단 HUD | 플레이 영역 상단의 어두운 가로 패널에 남은 시간, 배송 완료 수/전체 수, 누적 수익/목표 수익 표시 |
| 원형 미니맵 | 플레이 영역 오른쪽 위, 상단 HUD 아래에 고정. 전체 월드의 도로·건물 윤곽, 플레이어, 배송지, 출발지를 축소 표시 |
| 하단 화물 패널 | 플레이 영역 하단의 어두운 고정 패널에 화물별 식별자와 내구도 게이지 표시. 흔들림도 구분해서 확인할 수 있게 구성 |
| 오른쪽 배송 패널 | 플레이 영역과 분리한 밝은 패널에 미배송 집 식별자, 남은 마감시간, 경과 비율과 지각 표시 |
| 상황 안내 | 미니맵 아래 또는 플레이 영역의 고정 위치에 배송·복귀 안내 표시. 다른 패널과 겹치지 않게 배치 |

- 미니맵은 북쪽이 위인 전체 맵 고정 축척으로 구성한다. 플레이어를 따라 미니맵 자체를 회전하거나 스크롤하지 않고 마커 위치·방향을 갱신한다. 원형 테두리 밖으로 지도와 마커가 출력되지 않게 한다.
- 월드 종횡비를 유지해 미니맵에 맞추고 모든 맵 끝이 원 안에 들어오도록 축소한다. 배송 완료 여부는 색상만이 아니라 기호로도 구분한다.
- 카메라가 움직여도 상단 HUD, 원형 미니맵, 하단 화물 패널, 오른쪽 배송 패널은 화면 위치를 유지한다.
- 최대 9개 화물·배송지를 고려해 줄바꿈·목록 배치·스크롤 등 필요한 방식을 선택하고 잘림이나 겹침 없이 상태를 확인할 수 있게 한다.
- 구현은 월드 크기 설정 → 임시 지형 → 카메라 좌표 변환·추적 → 기본 미니맵 → 실제 데이터 HUD 순서로 작게 나눈다. 원형 미니맵과 최종 스타일은 기능 연결 후 완성한다.

### 7.2 [v3.0 추가] 살아 있는 일러스트 타이틀

**[사용자 확정]** 타이틀은 레이어 배경에 필요한 부분만 스프라이트 애니메이션을 섞고, 요소마다 움직임 속도와 반복 주기를 다르게 구성한다. 프레임 성능을 고려해 개발 단계를 나누어 적용한다.

현재 `game/modes/title_mode.py`는 `assets/images/title/title_background_v1.png` 한 장을 표시하고 오른쪽 벽면에 메뉴를 배치한다. 이를 비교 기준으로 사용한다. 아래 장면 구성·수치·성능 목표는 **[보완 초기안]**이며 자산 확인과 실측을 통해 조정한다.

#### 장면과 자산 구성

| 요소 | 표현 방식과 초기 범위 |
| --- | --- |
| 기본 배경 | 기존 골목·배달 분위기의 일러스트를 기반으로 하늘·건물·도로 등 고정 요소를 한 장으로 합성 |
| 원경 | 구름 등 독립 레이어 1~2개를 천천히 이동. 가장자리에서 끊김 없이 순환하도록 자산 여백과 반복 구간 설계 |
| 중경·전경 | 간판·잎 등 1~2개 요소를 작은 진폭으로 이동·회전. 회전 중심은 고정점에 맞추고 서로 다른 주기·초기 위상 적용 |
| 부분 스프라이트 | 캐릭터 옷자락 또는 오토바이 진동처럼 형태가 바뀌는 요소 1종부터 적용. 4~8프레임, 초당 6~10프레임으로 시작 |
| 추가 효과 | 먼지·빛 입자는 앞 단계 성능 확인 후 필요할 때만 적용. 동시 최대 8개, 고정 목록을 재사용 |
| 메뉴 | 배경 연출 위의 고정 화면 좌표에 출력. 움직이는 요소가 메뉴 글자와 선택 표시의 가독성을 해치지 않게 배치 |

움직일 요소는 투명 PNG로 분리하고 그 뒤의 가려졌던 배경까지 복원한다. 원본 배경에 같은 요소가 남아 이중으로 보이거나 이동 자리에 빈틈이 드러나지 않게 한다. 레이어는 공통 기준 해상도와 배치 좌표를 사용하고 실제 창 크기에 동일한 비율로 맞춘다. 이동·회전 여유를 포함해 화면 가장자리 노출을 점검한다. 스프라이트는 프레임별 중심·크기·색감과 첫 프레임에서 마지막 프레임으로 이어지는 반복 경계를 맞춘다.

자산은 `assets/images/title`에서 관리하고, 레이어 순서·위치·진폭·주기·시트 영역·재생 속도·효과 상한은 개발 시 `game/config/title_animation.py`에 모은다. 원본 전체 화면의 연속 프레임 대신 고정 배경과 작은 부분 자산을 조합해 사용한다.

#### 시간 처리와 리소스 수명

- 타이틀 전용 경과시간에 `game_framework.frame_time`을 적용하고 위치·회전·스프라이트 인덱스를 시간으로 계산한다. 시트 재생 속도와 화면 출력 FPS는 독립적으로 관리한다.
- 긴 창 이동·멈춤 뒤에는 적용 `dt`를 최대 0.1초로 제한하는 초기안을 사용한다. 지난 프레임을 순차 재생하거나 입자를 몰아서 생성하지 않고 현재 시각의 상태를 한 번 계산한다.
- 필요한 이미지와 시트는 타이틀 `init()`에서 한 번 로드해 공유한다. `update()`와 `draw()`에서는 파일 읽기·이미지 디코딩·리사이즈 이미지 생성·픽셀 가공을 수행하지 않는다. 프레임 선택은 로드한 시트의 영역을 잘라 그린다.
- 정적 요소는 제작 시 합성하고 움직이는 PNG는 필요한 영역으로 잘라 투명 픽셀의 중복 출력을 줄인다. 이미지 크기는 실제 출력 크기와 이동 여유를 기준으로 정한다.
- `finish()`에서 타이틀 이미지·시트·효과 목록·시간 상태를 정리하고 재진입 시 초기화한다. 실제 게임 진입 후 타이틀 갱신과 그리기가 계속 실행되지 않게 한다.
- 기존 키보드·마우스 메뉴 조작과 입력 우선 처리를 이어서 사용한다. 연출 도입 단계에서는 현재 연결된 시작·종료 동작을 검증하며 옵션·오토바이 변경 항목의 후속 기능은 별도 개발 범위를 따른다.

#### 성능 예산과 성능 저하 대응

| 항목 | 보완 초기안 및 검증 방식 |
| --- | --- |
| 기준 환경 | 현재 1280×720 창, 동일 PC·동일 수직 동기화 조건에서 정적 타이틀과 비교. 측정 시 CPU/GPU·Python/pico2d 버전·화면 주사율 기록 |
| 출력 목표 | 60Hz 환경에서 60FPS를 초기 목표로 설정하고 프레임 시간의 95백분위가 16.7ms 이내인지 확인. 지원 하드웨어 확정 후 수용 기준 조정 |
| 연출 처리 비용 | 정적 타이틀 대비 타이틀 갱신과 화면 제출 대기를 제외한 그리기 시간 합계의 95백분위 증가량 2ms 이내를 초기 목표로 사용 |
| 출력량 | 배경 포함 이미지 출력 최대 8회/프레임으로 시작. 입자 도입 시 개별 출력까지 포함해 최대 16회. 메뉴·폰트 출력은 별도로 측정 |
| 텍스처 | 타이틀 전용 디코딩 이미지 예산은 RGBA 환산 `너비 × 높이 × 4` 합계 32MiB 이내로 시작. 시트 전체 크기를 포함하고 실제 메모리도 함께 확인 |
| 측정 구간 | 로딩을 별도 기록하고 5초 준비 후 60초씩 정적/애니메이션 타이틀 비교. 평균 FPS·프레임 시간 95백분위·최대 지연·처리 비용·출력 횟수 기록 |
| 장시간·재진입 | 타이틀 10분 대기와 타이틀 초기화/종료 10회 검증. 효과 수 상한 유지, 메모리와 이미지 참조가 반복 횟수에 따라 계속 증가하지 않는지 확인 |

기존 `game_framework`의 FPS·갱신 시간·그리기 시간 지표를 재사용한다. 현재 평활 평균만으로 95백분위를 판정할 수 없으므로 검증 시 프레임별 표본을 고정 크기 버퍼로 수집하고 측정 종료 후 통계를 계산한다. `update_canvas()` 대기 시간과 실제 연출 처리 시간을 구분하며 프레임마다 로그를 출력하지 않는다.

예산을 넘으면 입자 제거 → 전경 효과 수 축소 → 이동 레이어 수 축소 순서로 조정하고 다시 측정한다. 조정 후에도 목표를 만족하지 못하면 정적 배경을 사용하는 경량 구성을 제공한다. 애니메이션 자산 로드 실패 시에도 기존 `title_background_v1.png`와 메뉴로 진입할 수 있게 한다. 기본 배경까지 실패하는 경우는 기존 리소스 오류 처리 방식을 따른다. 스프라이트 재생 속도 조정과 별개로 화면 출력·입력 처리는 목표 FPS에 맞춰 유지한다.

#### 타이틀 검증 기준

## 8. 데이터와 구현 구조

현재 파일 배치: 루트 `main.py`는 실행 진입점으로 유지한다. Python 구현은 `game/core`(프레임워크·게임 월드·디버그 설정), `game/config`(화면·주행 단계 설정 및 화물 종류), `game/world`(카메라·맵·도로), `game/objects`(오토바이·화물), `game/systems`(충돌·배송·진행 판정), `game/modes`(플레이 모드), `game/ui`(HUD·미니맵)로 나눈다. 기존 `ui.py`는 `game/ui/hud.py`로 옮긴다. 개발 문서는 `data/docs`, 맵 JSON은 `data/maps`, 이미지 리소스는 `assets/images`에 둔다. 리소스는 실행 위치가 아닌 프로젝트 루트를 기준으로 읽는다.

### 8.1 공통 설계 원칙

본 프로젝트는 Python과 pico2d를 기본 개발 환경으로 사용한다. 게임 화면 출력, 키보드 입력, 이미지·스프라이트 출력, 폰트, 사운드는 pico2d를 기반으로 구현한다. 오토바이 이동, 화물 흔들림·손상, 배송, 수익 계산, 충돌 판정, NPC 이동, 스테이지 진행은 Python 클래스와 모듈로 직접 구현한다.

#### 객체 지향 및 수업 구조 적용

LEC14의 게임 월드, LEC15의 게임 프레임워크, LEC16의 시간 기반 처리 구조를 프로젝트에 적용한다. 강의의 예제 캐릭터·조작·수치는 참고용이며 이 게임의 규칙으로 추가하지 않는다.

- 오토바이, 자동차, 보행자, 화물, 배송지는 각각 클래스로 구현하고 자신의 상태와 관련 동작을 관리한다. 객체별로 달라야 하는 위치·속도·내구도·애니메이션 상태는 인스턴스별로 보관한다.
- 월드에 등록하는 객체는 공통으로 `update()`와 `draw()`를 제공한다. 필요한 객체에만 `handle_event(event)`를 제공하며, 화물·정산 등 논리 전용 객체를 그리기 대상으로 등록할 필요는 없다.
- `game_framework.py`는 공통 게임 루프, 모드 전환, 프레임 경과시간을 관리한다. `main.py`는 화면 생성, 시작 모드 실행, 종료 정리를 담당한다.
- `play_mode.py`는 플레이 객체 구성과 입력 전달, 갱신 순서, 월드 및 HUD 출력을 조정한다. 타이틀·결과 모드는 해당 기능을 개발할 때 별도 모듈로 추가한다.
- 모드는 `init()`, `finish()`, `handle_events()`, `update()`, `draw()`를 기본 진입점으로 사용한다. 모드 스택이 필요한 경우에만 `pause()`와 `resume()`을 추가한다.
- 화면 모드와 4장의 배송 진행 상태를 구분한다. `DELIVERING`·`RETURNING`·`CLEAR`·`FAILED`의 판정은 `GameController`가 담당하며 모드 전환 때문에 기존 규칙이 달라지지 않는다.
- `game_world.py`는 객체 등록·제거·전체 정리 및 레이어별 갱신·그리기를 관리한다. 배경, 월드 객체, 전경 등은 레이어 순서로 출력하고 HUD는 카메라 변환 없이 출력한다.
- 객체 목록 순회 중 추가·제거가 필요하면 안전한 시점에 반영한다. 게임 월드 등록 순서에 게임 규칙을 의존시키지 않고, `play_mode.py`와 관련 시스템이 4.3의 처리 순서를 명시적으로 유지한다. [v2.4 보완] 같은 시간 구간을 중복 갱신하지 않는다. 시간 분할은 서로 겹치지 않는 하위 구간마다 한 번 갱신하며 합계가 해당 프레임 적용 시간을 넘지 않아야 한다.
- 필요한 클래스와 모듈부터 작은 기능 단위로 추가한다. 모든 화면이나 상속 구조를 처음부터 만들지 않으며, 공통 기능은 필요에 따라 조합·재사용한다.

#### 게임 루프 구조

초기화 단계에서 pico2d로 게임 화면을 생성하고 필요한 리소스를 불러온다. 이후 매 프레임 다음 순서를 반복한다.

1. 키보드 이벤트를 처리하고 현재 입력 상태를 저장한다.
2. 프레임 경과시간 `dt`를 초 단위로 계산하고 `game_framework.frame_time`에 저장한다.
3. 현재 모드의 `update()`에서 이동·충돌·화물·배송·수익·진행 상태를 갱신한다. 객체와 시스템은 동일한 프레임 시간 값을 사용하며 내부 순서는 4.3의 판정 우선순위를 따른다.
4. 화면을 지우고 카메라 변환을 적용한 월드 객체를 출력한다.
5. 고정 화면 좌표의 HUD 및 미니맵을 출력한다.
6. 갱신된 화면을 표시하고 다음 프레임으로 진행한다.

종료 시 리소스와 게임 화면을 정리한다. 초기화·리소스 로딩을 매 프레임 반복하지 않는다.

#### 시간 기반 이동 및 애니메이션

강의 구조에 맞춰 모드와 월드 객체의 `update()`는 인자 없이 호출하고, 필요한 곳에서 `dt = game_framework.frame_time`을 읽는다. 계산을 분리한 내부 함수에는 같은 `dt`를 인자로 전달할 수 있다. 프레임 경과시간은 프레임마다 한 번만 측정한다.

- 이동량은 `속도 × dt`, 속도 변화량은 `가속도 × dt`, 회전량은 `회전 속도 × dt`로 계산한다. 월드 좌표는 픽셀, 시간은 초, 속도는 픽셀/초를 기본 단위로 사용한다.
- 스프라이트의 애니메이션 프레임은 `frame = (frame + animation_fps × dt) % frame_count`처럼 실수로 누적하고 출력할 때 정수 인덱스로 변환한다. 갱신 호출 횟수마다 프레임을 1씩 증가시키는 방식은 사용하지 않는다.
- 배송 시간, 신호 주기, 화물 흔들림·손상 등도 같은 시간 기준을 사용한다. 애니메이션 재생 속도와 실제 이동 속도는 별도 값으로 관리하며, 보행 동작 등 필요한 경우에만 연동한다.
- `frame_time`은 프레임 간격이고 배송 경과시간은 별도 진행 데이터다. `RETURNING`에서도 이동과 애니메이션은 갱신하되 배송 시계와 수익은 기존 규칙대로 고정한다.

#### 입력 및 구현 원칙

- 기본 입출력과 렌더링은 pico2d를 사용하며 시간 기반 이동·손상 계산에는 `dt`를 사용한다.
- 키 눌림·해제 상태를 저장해 W/S/A/D 및 좌·우 Shift의 지속 입력과 여러 키의 동시 입력을 처리한다.
- Space는 직전 상태가 해제이고 현재 상태가 눌림인 순간에만 배송 입력으로 처리한다. 키 반복 이벤트를 새로운 눌림으로 취급하지 않는다.
- 게임 좌표 계산은 월드 좌표를 사용하며 카메라는 화면 출력 좌표로 변환한다.
- 게임 진행 상태와 화면 출력을 분리한다. 그리기 함수에서 배송·손상·정산 상태를 변경하지 않는다.
- 스테이지 차이는 설정 데이터로 관리하고 공통 로직을 재사용한다.
- 이미지·폰트·사운드 등 외부 리소스는 종류별 별도 폴더에서 관리한다.

#### 방향별 스프라이트 시트 및 방향 처리

현재 오토바이 초기 리소스는 운전자와 배달 상자를 포함한 16방향(22.5도 간격) 4×4 시트로 적용한다. 오른쪽을 0번으로 반시계 순서이며 한 방향당 한 프레임이다. 생성 이미지의 방향·중심·크기 편차는 프레임별 보정 설정으로 맞춘다. 초기 16방향 출력에서 드러난 방향 전환의 끊김과 프레임별 디자인 차이를 줄이기 위해, 기본 출력은 오른쪽 원본 한 프레임을 실제 차체 각도로 연속 회전시킨다. 원본 각도 오차와 중심 보정은 함께 적용한다. SPRITE_RENDER_MODE로 연속 회전과 기존 16방향 선택을 구분한다. 시트는 `assets/images/motorcycle/motorcycle_16.png`, 프레임 설정은 `game/config/motorcycle_sprite.py`에서 관리한다. 출력 전체 반경은 약 36픽셀로 기존 37픽셀 충돌 원 안에 들어가게 하며, 시트는 오토바이 초기화 시 한 번 불러온다. 정지·전진·가속·후진에서 같은 방향 선택 규칙을 사용하고 부스트 효과·주행 애니메이션은 아직 추가하지 않는다.

차체 각도와 이동 방향의 기준을 통일한다. 각도는 라디안, 0은 월드 오른쪽, 양의 회전은 반시계 방향을 기준으로 하며 `direction(angle) = (cos(angle), sin(angle))`로 계산한다. A는 양의 회전, D는 음의 회전으로 연결한다.

사람·오토바이·자동차는 방향별 스프라이트 시트를 사용한다. 현재 방향과 동작에 해당하는 프레임 영역을 선택해 pico2d의 `clip_draw()` 등 수업 환경에서 지원하는 잘라 그리기 API로 출력한다. 자동차는 해당 방향의 스프라이트를 선택한다. 오토바이는 사용자 주행 피드백에 따라 같은 탑뷰 프레임을 실제 차체 각도로 연속 회전해 표시하는 방식을 기본으로 사용한다. 16방향 프레임 선택 모드는 설정으로 유지한다.

실제 주행 각도는 연속값으로 유지하고, 출력 시에만 시트가 제공하는 가장 가까운 방향으로 대응한다. 방향별 그림 수 때문에 이동·회전 각도나 충돌·배송 판정을 제한하지 않는다. 오토바이는 차체 각도, 자동차는 주행 방향, 보행자는 이동 방향을 기준으로 프레임을 선택한다. 오토바이 후진은 속도 부호로 이동 방향을 바꾸며 후진한다는 이유로 차체 표시 방향을 180도 뒤집지 않는다. 정지 시에는 마지막 방향을 유지하고, 오토바이는 정지 중 A/D 회전도 표시 방향에 반영한다.

시트별 방향 수, 방향 순서, 동작별 프레임 수, 프레임 크기, 행·열 배치, 여백, 재생 속도는 리소스 설정으로 관리하며 이미지 제작 전에 결정한다. 방향 수와 크기는 아직 확정하지 않는다. 같은 이미지는 공유해 로딩하되 현재 동작·방향·프레임은 객체별로 관리한다. 스프라이트 선택과 카메라 변환은 화면 표현에만 적용하고 월드의 충돌 좌표계를 바꾸지 않는다.

게임 루프와 객체의 세부 구성은 수업에서 사용하는 pico2d 버전 및 프로젝트 구조에 맞춰 구현한다.

### 8.3 상태 및 데이터 일관성

- 배송은 완료 표시, 화물 제거, 보상 반영을 한 번에 처리한다.
- 결과 상태에서는 배송 및 보상 갱신을 중단한다.
- 재시작 시 시간, 수익, 배송 여부, 적재 화물, 차량·보행자 상태를 초기화한다.
- `RETURNING` 진입 후 배송 타이머와 수익을 수정하지 않는다.
- **구현 권장:** 내구도는 `0~최대 내구도`, 흔들림은 확정한 유효 범위로 제한한다.

#### 10.1.1 1단계 구성·성능 기준 확보 결과 (2026-11-18)

**현재 구조 확인**

- `main.py`는 1280×720 창을 `sync=True`로 열고 `title_mode`로 진입한다. 실제 수직 동기화 적용과 모니터 주사율은 측정 환경에서 별도 확인한다.
- `title_mode.init()`에서 배경 이미지와 `CachedFont`를 로드하고 선택을 0으로 초기화한다. 배경 PNG는 실제 1672×941이며 화면 전체로 맞춰 출력한다. `update()`는 현재 비어 있다.
- `draw()`는 화면 지우기 → 배경 이미지 1회 → 메뉴 4개·선택 사각형·선택 기호 → 화면 제출 순서다. 메뉴 문자열의 텍스처는 `CachedFont`가 재사용한다. 초기 선택을 유지하면 텍스트 이미지 5회와 배경 1회, 선택 사각형 1회가 출력된다.
- 키보드 위/아래·Enter 및 마우스 이동·좌클릭으로 선택한다. 시작은 `play_mode` 전환을 예약하고 종료·Esc·창 닫기는 루프를 종료한다. 옵션·오토바이 변경은 현재 동작이 연결되지 않은 항목이다.
- 메뉴 판정은 `menu_bounds()`를 출력과 공유한다. 1280×720에서 x=801~1216, 중심 y=432·356·280·204, 각 높이 54픽셀이다. 이는 pico2d의 왼쪽 아래 원점 좌표다.
- `game_framework`는 `perf_counter()` 기반 프레임 간격, 0.5초 단위 FPS, 평활 평균 갱신·그리기 시간을 제공한다. 기존 그리기 시간에는 화면 제출이 포함되고 `record_render_times()`는 그리기·제출의 평활 평균을 분리할 수 있다.

**장면 구성 결정**

실제 이미지를 확인해 노을 골목과 주차된 오토바이를 기준으로 아래 구성을 선정했다. 모든 좌표는 **1280×720, 왼쪽 위 원점**, 영역은 `(왼쪽, 위)~(오른쪽, 아래)`로 기록한다. pico2d 출력 시 중심 y를 `720 - 중심 y`로 변환한다. 원본 자산의 좌표는 x에 `1672/1280`, y에 `941/720`을 곱해 대응한다. 배치는 제작 시작 기준이며 분리 자산의 외곽선 확인 후 보정한다.

| `title_lamp_sheet.png`, 96×96 셀 4열×2행 | 384×192 | 0.281 | 선택한 셀 1회 |
| 애니메이션 구성 합계 | 배경 1개 + 부분 자산 4개 | 4.734 | 5회 |
| 기존 대체 배경까지 동시에 보유한 보수적 합계 | 전체 이미지 6개 | 10.736 | 활성 배경만 출력하여 5회 유지 |

이미지 예산 8회·32MiB 안에서 계획한다. 메뉴 문자열 이미지는 기본 5회가 추가되므로 총 텍스처 출력 예상은 10회다. 선택 색상 변경에 따른 폰트 캐시는 별도 집계한다. 출력 크기와 PNG 저장 크기는 구분하고, 프레임 시트 전체를 메모리 계산에 포함한다. 예산 초과 시 추가 입자 → 오른쪽 덩굴 흔들림 → 왼쪽 잎 흔들림 → 구름 순으로 줄인다. 등불까지 부담되면 복원 배경에 정적 발광을 합성해 경량 구성을 만든다.

**측정 방법과 실행 절차**

`game/profile_title.py`를 별도 실행 진입점으로 추가했다. 기존 `main.py`와 타이틀 메뉴를 통해 같은 창을 열고, 측정 실행 중에만 타이틀 함수에 시간 계측을 적용한다. 일반 `py main.py` 실행에는 계측이 적용되지 않는다. 이미지·애니메이션 제작은 후속 단계에서 진행한다.

측정은 타이틀 초기화 시간을 따로 기록하고 5초 준비 이후 60초간 완료된 프레임을 수집한다. 준비 구간과 겹치는 첫 프레임은 제외한다. 표본 상한은 65,536개이며 한도 초과 시 측정을 중단하고 `sample_capacity_exceeded`로 기록한다. 프레임 간격은 연속 화면 제출 완료 시각의 차이로 계산하며 입력·루프·계측 비용도 포함한다. 갱신·그리기·제출은 각각 측정하고, 그리기는 메뉴와 화면 지우기를 포함한다. 제출 시간은 `update_canvas()` 호출 전체로 제출과 수직 동기화 대기가 포함된다. 이 값은 GPU 실행 시간의 직접 측정값이 아니다.

통계는 수집 종료 후 평균·최근접 순위 방식 95백분위·최대값을 계산한다. 평균 FPS는 표본 수를 실제 표본 시간 합으로 나눈다. 연출 비교용으로 프레임별 갱신+그리기 합계의 통계도 기록한다. 측정 중 프레임별 로그는 출력하지 않는다. 완료하면 창이 종료되고 JSON 결과를 저장한다. 조기 종료·화면 전환은 `interrupted`, 예외는 `error`로 표시하며 정상 기준 결과로 사용하지 않는다.

프로젝트 루트의 PowerShell에서 다음 명령으로 재현한다. `py`는 pico2d가 설치된 사용자 Python 실행기를 사용한다.

```powershell
py -m game.profile_title --output .tmp/title_baseline.json --cpu "AMD Ryzen 7 5800H with Radeon Graphics" --gpu "AMD Radeon(TM) Graphics / NVIDIA GeForce RTX 3050 Laptop GPU"
Get-Content .tmp/title_baseline.json
```

측정 전에 Windows 설정의 시스템 → 디스플레이 → 고급 디스플레이에서 실제 게임 창이 표시될 모니터의 주사율을 확인하고 명령에 `--refresh-hz "확인한 값"`을 추가한다. GPU 목록과 실제 렌더링에 사용된 GPU는 구분해 기록한다. 창을 전경에 유지하고 65초간 메뉴 입력·창 이동을 하지 않는다. 결과의 `status`가 `complete`이고 `sample_seconds`가 약 60초인지 확인한다. 이후 같은 조건으로 애니메이션 타이틀을 측정해 비교한다.

**기존 정적 타이틀 측정 결과**

2026-11-18 14:50 KST에 위 계측 진입점으로 측정을 완료했다. 결과 원본은 로컬 `.tmp/title_baseline.json`에 저장했다. 5초 준비 후 **60.001초·6,606프레임**을 수집했고 상태는 `complete`다. 프레임 95백분위는 초기 목표 16.7ms 안에 있지만 최대 52.080ms 지연이 관찰됐다. 주사율이 확인되지 않았으므로 60Hz 환경의 최종 성능 통과 판정은 보류한다. 향후 같은 조건에서 갱신+그리기 95백분위 증가량을 이 기준의 1.281ms와 비교한다. 직접 GPU 처리 시간·프로세스/VRAM 실사용량·입력 반응 지연은 이번 측정에 포함되지 않았다.

1단계의 코드 구조 확인·실제 정적 측정·장면 설계·예산 계산은 완료했다. 남은 확인 항목은 실제 출력 모니터 주사율과 렌더링 GPU 기록이며, 애니메이션 성능 비교는 3~4단계에서 수행한다. 자산 생성과 움직임 구현은 아직 착수하지 않았다.

**2단계 작업 순서**

1. 원본 1672×941에서 공통 1280×720 구도로 작업 기준을 만들고 메뉴 안전 영역과 위 좌표를 맞춘다.
2. 구름·양쪽 잎·발광부를 분리하고 하늘·처마·벽·등불 뒤 배경을 복원한다.
3. `title_background_v2.png`와 구름·덩굴·나뭇잎 PNG를 위 예산 크기로 제작한다. 시트는 4단계 제작을 위해 발광부 기준 위치와 정적 모습을 먼저 확보한다.
4. 레이어 순서·출력 영역·고정점·주기를 `game/config/title_animation.py`에 기록하고, 2단계에서는 모든 레이어를 정지 상태로 합성한다.
5. 자산 초기 로딩·종료 정리와 기존 배경 대체를 연결하고 중복·구멍·잘림·메뉴 가독성을 확인한다. 시트 제작 전에는 정적 발광을 사용한다.
