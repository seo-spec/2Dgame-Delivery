# 4단계 결과 — 마감·가독성 및 시작 지연 수정

2026-11-28. art-direction.md, stage3-result.md, stage3-assets.svg와 실제 타이틀/상점/주택/나무/정류장/아파트 PNG, 지면·배치·고객 표시 코드를 확인했다. 게임 실행·자동 테스트·커밋은 하지 않았다.

## 시작 시 응답 없음: 코드에서 확인한 원인과 수정

play_mode.init → RoadMap → RoadFinish 경로에서 기본 지면21개와 독립 진입부4개를 동기 생성한다. 기본 지면만 패딩 포함9,832,736픽셀이다. 각 픽셀의 잔디/아스팔트 계산 외에 보도·진입부·표시선 합성도 반복한다. 기존에는 매 시작/재시작에 같은 작업을 다시 수행하며 합성 루프에서 창 이벤트를 처리하지 않았다. 이는 사용자 제보의 유력 원인이지만 프로파일링으로 확정한 유일한 원인은 아니다.

수정:
- .tmp/ground-cache에 최종 RGBA를 zlib로 압축해 구역별 저장한다. 같은 맵/미술 코드에서는 재시작·재실행 때 픽셀 합성을 생략하고 초기화 때 GPU 업로드만 한다.
- 캐시 키에는 맵 설정·도로 사각형·월드 크기·관련 소스의 SHA-256을 포함한다. 변경된 미술/도로 데이터에 오래된 지면을 적용하지 않는다.
- 손상·불완전 캐시는 압축 체크섬/기대 크기를 확인해 재생성한다. 임시 파일을 완성한 뒤 교체하고, 읽기/쓰기 실패 시 기존 합성 경로로 계속 진행한다. 캐시는 Git의 기존 .tmp 제외 규칙에 해당한다.
- 캐시가 없는 첫 합성에서는 16행마다 시간 확인 후 약50ms 간격으로 SDL_PumpEvents를 호출한다. 실제 호출 간격은 행 처리 시간에 따라 달라질 수 있다. 입력/종료 이벤트를 큐에서 꺼내 버리지 않으며 SDL 작업은 기존 메인 스레드에 둔다.
- 같은 월드2px 셀에서 도로 마스크·조용한 구역·연석 음영·알파가 같을 때만 RGBA 계산을 공유한다. 두 행 분량만 보관한다. 전체 맵의 픽셀별 Python 사전을 상주시키지 않는다.
- 반복 팔레트 변환은 최대256개 조합만 캐시한다. 기존 정수 색상 결과와 도로 경계를 유지하는 최적화다.
- 콘솔에 '[지면 준비] 캐시 n/25, 재생성 m, …초'를 남긴다. 구역 로드 실패가 없을 때 전체25개다. 이 시간은 지면 준비만이며 전체 시작 시간/FPS가 아니다.

첫 실행이나 미술 코드 변경 후에는 지면 합성이 여전히 필요하다. 로딩 화면을 새로 넣거나 비동기 로딩을 구현한 것은 아니다. 이 수정으로 응답 없음과 지연이 실제 해소됐는지는 미확인이다.

## 확인한 미술 불일치와 수정

1. 독립 진입부의 투명 바탕 RGB가 이전 GRASS_COLOR였다. 가장자리 혼합에서 새 올리브 지면과 다른 어두운 녹색을 사용했다. 이제 v2 잔디를 혼합하고 진입 포장도 v2 작업 마당 팔레트로 맞춘다. 문턱의 밝은 대비와 모든 진입부 좌표는 유지했다.
2. 상점 공통/입구에 같은 지붕 보완 사각형을 적용해 서로 다른 내부 테두리를 고려하지 않았고, 두 개의 큰 설비 복원 사각형에 주변 지붕까지 포함했다. 공통 지붕과 입구 지붕의 보완 범위를 각각 내부 면에 맞추고, 설비는 환기구2개·실외기·배관의4개 범위로 나눴다. 초기화 합성만 바뀌며 원본 PNG·문·건물 크기·GPU 텍스처 수는 유지한다.

[stage4-assets.svg](stage4-assets.svg)는 현재 정규화/상점 보완을 준비 크기로 표현한 참고 보드다. 게임 캡처가 아니며 SDL 축소의 반올림·필터링 결과와 최대1px 차이가 날 수 있다. stage3-assets.svg는 당시 합성 범위의 기록으로 보존한다.

## 자원·동작 유지

GPU 텍스처 크기·개수와 프레임당 월드 출력 수는 3단계와 동일한 설계다. 추가 디스크 캐시는 실제 생성 전이므로 압축 파일 크기 미측정이다. 압축 전 기본 지면은39,330,944바이트이며 진입부4개가 별도로 있다. 상점 설비 합성 호출은 초기화 시에만 늘고 프레임당 출력은 그대로1회다.

건물·소품 위치/표시 크기·고객·충돌·도로/배송 판정·입력 조건은 바꾸지 않았다. 차량·고객·HUD 파일, 원본/v1 PNG는 수정하지 않았다. 기존 Python 캐시 변경은 작업 전부터 있었고 이번에 실행하거나 정리하지 않았다.

## 수동 확인 순서

1. 타이틀에서 시작한다. 캐시가 없으면 합성 대기 후 진입되는지, 창이 응답 없음으로 바뀌는지 확인한다. 콘솔의 지면 준비 시간을 기록한다.
2. 같은 게임에서 재시작하고, 프로그램 종료 후 다시 시작한다. 정상 저장됐다면 '캐시25/25, 재생성0'인지 확인하고 첫 시작과 비교한다. 폴백이 발생하면 전체 수가 달라질 수 있다.
3. 첫 합성/캐시 진입 화면이 같은지 비교하고, 종료 요청·이동 입력이 로딩 후 정상 처리되는지 확인한다. 캐시 파일이 손상되거나 쓰기 불가일 때도 원래 합성으로 진입하는지 확인한다.
4. 두 배송 상점과 일반 상점의 지붕 구멍·보완 경계·환기구2개·실외기·배관 잘림·문 가림을 확인한다.
5. 다섯 배송 입구와 도로 이음부를 순회하며 진입부 가장자리 색 띠와 문턱 연결을 확인한다.
6. 미수령→수령→임박/지각→파손/완료→복귀/실패에서 고객/!·차량·안내·HUD의 가독성과 기존 상호작용을 확인한다.
